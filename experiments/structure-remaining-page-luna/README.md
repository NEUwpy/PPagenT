## 本次要验证什么

用户提出：先按全页稿件安排形状或图片的位置与大小，然后扫描剩余页面；文字沿用正常整页排版能力，只是可用页面不再是一个完整矩形。

本次用 Luna high 对既有三页稿件重做：四项交接条件、四层反馈筛选、四级维护能力。固定中性 Skin 和原结构造型。成功标准同时包括事实完整、真实调用、字体层级、图文归属、语义断行和整页阅读关系。调用或碰撞检查通过不等于整页验收通过。

## 最小实现

- `prepare.mjs` 在计划好的实际尺寸渲染结构，提取真实对象占位和文字锚点，供排版前读取。
- `scan.mjs` 将正文页面减去占位与必要留白，得到各水平带上的自由区间。它不预先规定文字框数量、宽高或角色。
- Luna 根据稿件语义和剩余页面决定文字组合、层级与位置，然后用 `harness.mjs` 真实调用结构、生成可编辑 PPTX、重新导入并渲染 PNG。
- `gallery.mjs` 保留每次尝试，支持显示定位框、实际占位、剩余页面和最终文字框。`pptx-checks.json` 检查源文字进入 PPTX、字号档位和原生对象数量；稿件语义与视觉质量另行人工审查。

占位复用前一轮 `../structure-occupancy-pilot/occupancy.mjs`：按实际对象包围框计算，P3 保护每一级的语义组合及留白。它能释放阶梯两侧空间，但并非任意曲线的像素级轮廓识别，也不意味着每个空隙都应该写字。

## 对照与限制

旧稿见 `../structure-wholepage-luna-20260908/` 和 `../structure-occupancy-pilot/`。本轮保持相同稿件、结构实现和 Skin；增加预扫描流程，同时明确了文字排版要求。因此观察到的改善不能单独归因于扫描算法，需要更多稿件与独立运行才能判断稳定性。

只在实验目录验证，没有把这套机制接入正式 Layout 或推广到全结构库。最终文字仍以可编辑矩形文本对象绘制；剩余页面描述负责给出可用空间，段落形态由排版决定。

## 本轮结果

三页整页验收为 **0/3**。7 次 `renderCase` 记录中，4 次导出 PPTX，3 次因碰撞或外部文字溢出拒绝。P3 第三稿重用编号的三次调用均保留并计数，没有用最终记录掩盖中间拒绝。

P1 的主张、便签阵列和底部说明缺少共同对齐关系；P2 的依据与漏斗相距过远；P3 前两稿仍重复、出现孤立标点，第三稿尝试进入阶梯左上空白但未通过碰撞与容量检查。P1/P2 和 P3 第三稿已分别准备并读取扫描结果；P3 前两稿把准备和预写文字放在同一脚本，不能证明模型按新流程规划。

四份 PPTX 的源文字和字号档位检查通过，实际 PNG 均已复核。P1/P2 的文字和主体为原生对象，图标是嵌入 SVG 并带 PNG 回退，不能宣称所有图标都已拆成原生路径。P3 为 42 个原生形状／文字对象。HTML 不溢出也没有阻止 P3 第二稿在 PPT 渲染中出现句号孤行。

结论：扫描提供的几何信息可用，但单独增加扫描步骤没有解决本轮文字排版问题。后续应验证正常文字排版如何利用剩余页面，并把段落测量、图文对齐和必要的结构位置调整串在一起；本轮不支持扩大到全库。
