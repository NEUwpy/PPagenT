# 结构线索解析器最小 A/B/C

本实验只调用内容阶段，不进入视觉导演、渲染或 PPTX。输入取自《为什么做 PPagenT》的两个真实难点：

1. “稳定 80 分 vs 随机 95 分”：应识别为两个对比主节点；组内短条目属于后续 Visual Skill 的 `componentBindings`。
2. “作品 → 规律 → 能力”：应保持三个主节点，并把“表达、容量、变化、禁忌”放入“规律”的节点内 `points`。

## 结果

| 方案 | API 请求 | 墙钟时间 | 总 Token | 对比主节点 | 转化主节点 / 中间分点 |
| --- | ---: | ---: | ---: | --- | --- |
| A：内容导演直出 | 1 | 7.5 s | 3306 | 错误：拆成观点、场景、结论 3 项 | 错误：2 个主节点，4 个分点粘成 1 句 |
| B：逐 cue 局部解析 | 4 | 14.6 s | 5875 | 正确：稳定 80 / 随机 95 | 正确：3 个主节点 + 4 个独立分点 |
| C：单次批量解析 | 2 | 9.4 s | 4662 | 正确：稳定 80 / 随机 95 | 正确：3 个主节点 + 4 个独立分点 |

B 组实际命中两个 cue，但其中一个结果第一次不满足容量约束而重答，因此形成 3 次结构请求加 1 次内容请求。C 组把两个 cue 合并为 1 次结构请求，再调用 1 次内容导演；相对 B 组请求数减半、时间约减少 36%、总 Token 约减少 21%，本样本中没有损失结构正确性。

## 架构判断

- **不能直接删掉结构提示。** A 组证明当前 DeepSeek 内容导演仍会把语义骨架整理成叙事段落，主节点和节点内分点都会错层。
- **逐 cue 请求不适合长期默认。** 它有效，但稿件中 cue 越多，请求数和失败重答越多；这正是链路继续变重的来源。
- **批量结构预读是当前更合理的候选。** 它不增加新的业务对象，只把现有局部请求合并；程序仍负责先检测高置信片段，模型只提取这些片段的原子结构。
- **本实验没有证明比较页的小点已经闭环。** 比较页的两个主块属于内容层，左右各 1–5 个可见短条目属于 Visual Skill 的 `componentBindings`。后者必须从来源语义中压缩，不能为了两侧均衡虚构内容。
- **不立即迁移生产实现。** 当前只有一个两页样本。下一项最小验证应使用完整《为什么做 PPagenT》稿件，但仍只跑内容阶段；确认批量请求没有漏 cue、串页或错配后，再替换逐 cue 实现。

## 复现

```powershell
node experiments/architecture/structure-reader-ab-20260814/run-ab.mjs
```

已有 A/B 结果时只补跑批量组：

```powershell
node experiments/architecture/structure-reader-ab-20260814/run-ab.mjs --batch-only
```

结果写入 `result.json`。本地 API Key 只从 Git 忽略的 `config/deepseek.local.json` 或环境变量读取，不写入实验产物。
