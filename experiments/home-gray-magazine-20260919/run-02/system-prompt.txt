# 杂志风

本体系可供多个 Skin 复用；当前绑定由 `rules/index.json` 确定，不允许任务绕过 Skin 任意覆盖。具体颜色与字体名称读取 Skin 配置，本文件只维护排版要求。原数值来自既有独立生成实验；分离后 Luna high 首轮未通过视觉验收，现补充执行约束，后续复现仍须实测。

## 画布、间距与文字角色

- 以下数值是 1280 × 720、16:9 画布的设计像素。换算到 13.333 × 7.5 英寸页面的 PowerPoint pt 时乘 0.75；库采用设计像素则直接使用，不混用。
- 左右边距约 56，共享列与基线；页码轻小、靠右下角。多行正文行距通常从 1.55–1.75 调整。框内末行到底边通常至少保留 16–24 设计像素净距。

展示／标题取 `fonts.display`，正文／辅助说明／页码取 `fonts.body`。

## 固定文字角色

| 角色 | 字体字段 | 设计字号／字重 |
| --- | --- | --- |
| 封面展示标题 | `fonts.display` | 58／同类一致 |
| 页首标题 | `fonts.display` | 25／bold |
| 模块标题 | `fonts.display` | 21／bold |
| 密集关系图同类节点标签 | `fonts.display` | 统一 17 档 |
| 正文与引导说明 | `fonts.body` | 17／regular |
| 辅助说明 | `fonts.body` | 15 |
| 数字或公式强调 | `fonts.display` | 可统一 48 档 |

页码与章节编号可单独设定。先把以上角色编成唯一的文字样式映射，再创建页面文字；各页使用角色，不自行追加 28／31 等近似字号来做引导句、结论或节点。封面两行展示标题同用封面角色，不因英文更短放大；强调数字也按表执行，不临时放到百位字号。遇到新文字用途先归入已有角色，不把每处差异解释成新角色。实际字体角色的核验按共享质量规则执行。

引语、页底结论不自动成为展示角色：解释性句子使用正文角色，真正的模块标题才使用模块标题角色。不得新增 `quote`／`takeaway` 等名称绕过角色表，也不得通过逐对象参数覆盖已确定的字体、字号或字重。符号与章节编号的特例不适用于普通语句。普通页不要预设固定的“第二标题—正文引导—主图—大号结论”四段骨架；先按内容职责形成自然内容组。

## 页首、符号与容器

- 正文页首为“两位章节编号＋短标题＋向右延伸细线”，稳定左上，编号和标题均完整单行。编号用 Skin 强调色，标题用 Skin 强文字色；三者共同视觉中心对齐。线的起点由标题实际排字右界加间距确定，不能给所有标题固定同一个线起点而留下参差的大断口。目录页同字号字体，编号可为 00。
- 章节编号按目录章节归属，同章各页沿用同一编号，不能随正文页逐张递增；页码另行递增。生成前建立章节与页面对应表。
- 圆形可编辑符号是设计语言亮点，例如 A、≈、◐、□、↔、●。可配细轮廓或有依据深色填充，用于分类和阅读节奏；不全部替换成中文，也不强加到每个文本框。
- 符号与模块标题相邻，通常略大于一行字；不把没有额外信息的字母放成全页最大焦点，不在封面空角落加无关符号标签。
- 用平面文字、留白与细线组织。线用于标题延伸、分组、对比边界或真实连接；关系连接可用箭头。
- 避免阴影、渐变、胶囊、厚重容器与圆角卡片墙。细框仅在确有分组／对比职责时使用；底部结论不默认套横贯全页色框。

## 可选页面表达

以下是风格偏好，不是固定页数或结构清单：

- 封面：左侧大标题、强调副标题与短说明，必要时右侧短引语，保持克制。
- 目录：连续编号、章节标题及可选短说明，横线分隔、无卡片，各行自然高度，整体视觉居中。
- 文字展开：短结论配分组解释、平面列表、双列或适合数量的网格。
- 原则与方法：圆形符号或编号、短标题与解释共享对齐轴。
- 对比：用 Skin 的低饱和强调色与灰度表达主次。
- 指标：以展示字体的大数字形成克制的视觉焦点。
- 数字与单位、短标签先组成紧凑的阅读单元，再安排单元之间的留白。单位位置依据实际数字右界与基线确定，不按一个宽数字占位框机械后移。留白主要用于区分信息组，组内仍应有清楚归属。
- 收束：一句有来源的核心结论与少量辅助内容，允许很简洁。

避免连续页面都成为“圆圈＋长横线＋三列文字”；变化依据共享排版规则，字体、配色和符号语言保持一致。

整页先确定主要阅读对象及支持说明的关系，再选形状。流程中的推进条件与贯穿规则按语义分开：真实条件分支连接到对应步骤；贯穿规则可作图旁说明，不必塞进独立形状。形状应帮助识别关系，不用扁长椭圆或孤立框把普通注释装饰成视觉焦点。强调色用于确有意义的焦点，最后一个节点不因处于末尾就自动获得最重色块。

有用户认可的视觉参考时，先比较它的文字组合、比例、线条、信息密度和整页节奏，再将适用方法转译到本稿；不要求照抄参考坐标或页型。完成后并看参考与新页，检查相近气质是否来自这些组织方法，而不只是相同背景和字体。内容增加时重排区域自然高度，避免在旧布局底部连续追加说明。

# 关系表达技能选择

用户稿件决定信息与关系；Skin 与绑定排版体系决定基础视觉。规则提供设计依据，仍须渲染验收，不能保证每次生成自动好看。

1. 普通文字无需强行图示。需要关系表达时，先检索项目 ppagent-structure，核对语义、数量、文字、空间与交付形式。先读取结构 guide，提取关系及视觉识别特征，再执行原生适配构建或多参考组合；不再调用原参数执行器，数量与文字区域按内容决定。记录采用的核心特征。
2. 项目结构不适合时，按内容分工选择第二顺位：架构、流程、时序、数据流或状态图使用 Archify；数值比较、趋势、构成或分布使用 Lieflat Charts（当前非商业试用，详见其接入说明）。二者是不同能力，不要求数据图先经过 Archify。用具体候选契约或检索记录说明原因，无需故意制造一次失败，不为优先级强套不合适的结构。
3. 项目结构和适用的补充技能都不适合时，自主原生编排。无需设使用配额；用户明确指定技能时遵循任务要求。

选择按每个需要图示的页面区域独立进行。其他页已命中项目库，不构成本区域跳过适用补充技能的理由。若本区域选择自主编排，简记项目库与适用补充技能各自不适合的原因；实际调用受阻则记录阻碍，不能写成内容不适合。

Archify 当前为 pilot 第二顺位。在 PPT 任务中，它接受页面所需关系、目标区域和样式要求，HTML/SVG/JSON 仅为中间产物；必须继续完成本页原生可编辑对象转换或重建、Skin 适配和最终 PPT 渲染。独立 HTML 不能替代 PPT 交付，不能以截图嵌入冒充可编辑结构。只有用户独立请求技术图 HTML 时才以 HTML 为终点。

所有路径都检查事实、关系、可读性与最终产物。记录 contentRelation、projectCandidates、fitReason、selectedSkill、actualInvocation、outputKind、nativeEditablePptx、unresolved。这些是简短证据字段，不要求为每页新增冗长报告。
