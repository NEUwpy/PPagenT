# 第一顺位覆盖边界测试稿

## 稿件：异步报告导出

用户端向导出 API 提交报告请求。API 先将任务放入队列，再立即返回任务编号；这个响应仅表示已受理，不表示文件已经生成。

后台 Worker 随后向队列领取任务，队列返回任务数据，Worker 执行文件生成。稍后用户端携任务编号向 API 查询，API 向 Worker 查询状态，Worker 返回“已完成”及文件地址，API 才向用户端返回文件地址。

参与者必须保持为用户端、导出 API、任务队列、Worker。图中须保留各消息的发送方、接收方、时间先后及请求/返回区别，尤其区分“返回任务编号”和“返回文件地址”。本稿为模拟过程，未指定或宣称真实系统架构。

## 第一顺位为什么可能不适配

当前 catalog 暴露 35 个可调用资产；sequence 仅普通顺序流程和阶段门禁。role-stage 还有阶段角色泳道，network 有内外协同生态网络。不能只查 sequence 就断言全库无候选。

- 普通顺序流程承载 3–6 个步骤，不原生表达参与者间逐条消息及返回。
- 阶段门禁要求阶段之间有检查/决策门槛，本稿没有这样的门禁关系。
- 阶段角色泳道表达阶段与职责两个维度，需进一步 inspect 核对有无消息/返回接口；仅“有角色”不等于能直接表达消息时序。
- 生态网络明确不适合有明确顺序、需要逐条连线说明的场景。

如果必须增加生命线、独立消息行和返回样式才能表达，已经属于重建时序图。此时优先尝试第二顺位专门的 sequence 能力比强套项目模板合理。这是父任务的候选分析；Luna 自身的判断和调用仍需单独保留。

成功条件：Luna 真实检索第一顺位、说明不适配原因，实际使用合适的第二顺位并保留稿件语义。程序校验与视觉验收分开报告；若不能合法运行浏览器检查，明确视觉未验收。
