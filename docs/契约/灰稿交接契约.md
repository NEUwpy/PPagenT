# 灰稿交接契约 v0.1（main / home 对接提案）

2026-09-30。用户要求先确定中间字段与灰稿形态，保存到 Git，之后由 main 阅读并与 home 对齐。本文件固定一份可检查的提案；**main/home 尚未完成接口确认，现有生产入口尚未接入此交接包**。本次不启动模拟灰稿批次。

## 一个内容来源，两种编译结果

**结构化页面表达是中间状态的真源；灰稿是它的可视化编译结果。** 用户检查灰稿，是在检查这份契约的页序、内容归属、关系、表达和承载。表单也是同一契约的编辑/检查投影。

```text
main：原稿 → 来源与页面表达 → 合法能力选择与绑定 → gray-handoff.json
                                                         ├─ 灰稿编译 → 灰稿 PPTX / 完整预览
home：gray-handoff.json + Skin / 风格 ─────────────────────└─ 成品编译 → 成品 PPTX / 完整预览
```

两段读取同一个交接包。正文只在 `plan.pages[].groups[].blocks[]` 等内容字段中维护；布局、表达选择和槽位绑定引用 ID，不再填写第二份标题或正文。`sources` 保存原始证据，与提炼后的上屏文字职责不同。

灰稿 PNG/PPTX、编译后的 `state.json`、几何、测量、审阅和日志均为派生产物。修改页面内容或布局语义时，回改交接包、升修订号、重新编译；不把手改 PPT 或截图识别结果作为回写内容。

## 交付文件与身份

| 文件 | 内容与职责 |
| --- | --- |
| `gray-handoff.json` | 唯一交接输入；字段见本文件与 [Schema](../../schemas/gray-handoff.schema.json) |
| `gray-draft.pptx`、`preview/` | 同包编译的可读灰稿与逐页完整预览 |
| `derived/gray-state.json`、`derived/layout-receipts.json` | 从交接包计算的兼容运行状态、区域与容量回执；只读 |
| `manifest.json` | 契约 ID/修订/指纹、编译器与资产版本、文件路径及 SHA256、编译/审阅状态 |

这里固定逻辑文件职责，不强制搬迁历史 run 目录。历史产物仍按真实 `state.grayDraft.artifactDirectory` 定位；新包要由导出适配器生成，不能仅把旧文件改名。

`contractId` 标识一份交接，`revision` 为正整数。页序取 `plan.pages` 数组顺序，组内阅读顺序取 `readingOrder`（省略时为 groups 顺序），块顺序取 blocks 顺序；不再增加另一组 `order` 字段。

## 顶层字段

| 字段 | 必填 | 形态与约束 |
| --- | --- | --- |
| `schemaVersion` | 是 | 固定 `gray-handoff-1`，作为提案的机器形态版本 |
| `contractId`、`revision` | 是 | 稳定 ID、正整数修订号 |
| `origin` | 是 | `{kind:"real|simulated", note}`；真实稿与模拟输入始终分开标记 |
| `canvas` | 是 | `{width,height,unit:"px",scope:"content-area"}`；灰稿内容区，不是成品整页尺寸 |
| `sources` | 是 | `[{id,heading?,text}]`；真实输入来自来源切段，模拟输入须提供明确标记的模拟证据 |
| `plan` | 是 | 沿用 `gray-plan-3` 内容，不新建一套同义 PageBrief/PageView 正文 |
| `pageBindings` | 是 | 逐页版式选择、区域归属、表达选择和槽位绑定；与 plan 页序一一对应 |
| `freeze` | 是 | `{status:"draft|frozen",contentSha256,bindingSha256}`；冻结指纹保护内容和布局语义 |

`origin.note` 记录输入来源、建设目的及真实稿文件/哈希定位。当前来源项形态复用 `state.sources`。来源文件列表、媒体和数值数据的结构化资源契约需 main/home 在启用对应能力前确认，不把路径字符串当成已接入的数据能力。

## 内容字段：复用 gray-plan-3

| 层级 | 字段与含义 |
| --- | --- |
| 整稿 | `schemaVersion:"gray-plan-3"`；`deckBrief:{title,audience,objective}`；`pages`；可选 `planningNotes` |
| 页 | `pageId`、`title`（页名）、`claim`（实际上屏主题句）、`pagePurpose`、`narrative`、`groups`；可选页级 `sourceIds`、`readingOrder`、`relations`、`visualMapping` |
| 组 | `id`、`role`（实际内容职责）、`heading`、`importance:"primary|supporting"`、`kind:"text|diagram|flow|chart|table|image"`、`blocks` |
| 正文块 | `id`、`text`、`sourceIds`；可选 `label`、`kind`、`scope` |
| 表达要求 | 非 text 组或非 text/note 局部块提供 `expression`、`relationship`、`production`；属于表达说明，不是成品正文 |
| 共同说明 | `scope:"group"` 的文字块作用于本组，不编号；组内仍须有普通条目 |
| 附注 | `kind:"note"` 紧随所依附的文字块，不编号；沿用当前相邻归属规则 |
| 显式关系 | 可选 `relations:[{from,to,type,meaning}]`；沿用当前关系类型与 `$claim` 端点，不强迫所有页新增关系图 |

重要限定保留在实际上屏文字中，来源留在 sourceIds。此提案不再增设另一份 `qualifiers` 或改名为 `thesis`。`title` 与 `claim` 是现有两个不同职责，home 不自行互换或改写。

ID 作用域：pageId 整稿唯一；group.id 本页唯一；block.id 所属组内唯一。跨层引用必须带 pageId 的上下文和 groupId，不能只凭裸 blockId 找内容。组 ID 和块 ID 不包含 `/`，从而兼容现有 `groupId/blockId` 的 sourceLocation。

`visualMapping` 沿用现有引用式映射，绑定器检查覆盖与支持关系；没有映射时不推断六个块就是六个同级卡片。不得把组间支持、归属或比较关系降格为纯几何分区。

## 形态与绑定字段

每个 `pageBindings` 项：

```json
{
  "pageId": "p1",
  "layout": {"layoutId": "category-container", "parameters": {"type": "single"}},
  "regions": [{"regionId": "r1", "groupId": "g1"}],
  "expressions": [{
    "expressionId": "e1",
    "regionId": "r1",
    "sourceLocation": "g1",
    "kind": "text",
    "contentRefs": [{"groupId": "g1", "blockId": "b1"}],
    "selection": {"status": "selected", "programId": "source-text-v1", "reason": "沿用本组文字归属"},
    "parameters": {},
    "slotBindings": []
  }]
}
```

| 字段 | 责任与约束 |
| --- | --- |
| `layout.layoutId` | 已登记页面版式/候选的命名 ID；当前兼容例子使用 gray-templates 中的 ID，不能宣称它们已是完整的新两级版式库 |
| `layout.parameters` | 当前先沿用 `{type:"single|row|column|grid",weights?,columns?,children?}`；仅程序求解几何，组合叶子按阅读顺序恰好覆盖全部组一次，最多三层 |
| `regions` | MVP 每组一个逻辑区域；只记录 regionId 与 groupId。区域比例由布局参数决定，实际 x/y/width/height 是编译回执 |
| `expressions` | 本页每组的表达或局部表达。regionId 指定所属区域，sourceLocation 使用现有的 `g1` 或 `g1/b1`；contentRefs 列出本表达真正承载的块 |
| `selection` | `selected` 表示已经选中命名能力；`missing` 表示缺能力，仅可保留在 draft。selected 不代表容量或视觉通过 |
| `parameters` | MVP 只接受数值、布尔及资产登记的字符串状态选项，例如 showStatus；节点数组与正文通过 slotBindings 构造，不手填第二份文字 |
| `slotBindings` | `[{target,contentRef:{groupId,blockId?,field}}]`；target 是资产参数路径，如 `levels[0].title`，不是旧测量样例的像素文字框 ID |
| `capacityRef` | 选定结构时必填 `{path,sha256}`，文字程序可省略；固定所消费资产的槽位/容量声明。引用只证明使用哪版声明，实际文字与目标区域仍需测量 |

`contentRefs` 的普通正文块在本页恰好被一个表达承载；scope:group 和 note 必须与所依附内容同属一个表达。heading/label/text/id 的 slotBindings 只引用本表达拥有的内容，不能从别组摘取正文。结构可以带本组标题，但未绑定的其他上屏字段必须由文字层承载，编译器要报告完整性缺口。

文字程序使用整个原组及已声明的 visualMapping 回填，slotBindings 为空。结构参数由“非正文参数 + 字段引用解析”构造，例如 `levels[0].title ← g1/b1.label`、`levels[0].body ← g1/b1.text`、`levels[0].key ← g1/b1.id`。这一步属于确定性程序；模型不生成渲染代码。

非文字表达不能只引用一段自由文字后让 home 猜节点。节点、关系、图表数据和媒体必须有可以确定性绑定的字段。当前例子覆盖文字与已有结构的普通节点字段；局部图示、表格、图表、图片及多图示页要逐项确认资源和绑定规则，缺口保留为 missing，不伪造可用能力。

## 灰稿应显示的形态

1. 页标题/主题句、组标题与真实文字可读；主次、归属、共同说明与附注可见。
2. 按所选版式编译区域轮廓、相对比例、阅读方向和局部结构占位。结构可用简化轮廓显示，但成员与关系来自同一契约。
3. 制作说明可以用浅蓝区域显示，用于检查表达作用和要求；正式成品不把这些说明自动当正文。
4. 调试模式可显示 page/group/block/region/expression ID 及能力缺口。调试标签是投影，不进入内容字段。
5. Skin 的最终装饰、字体细节、图标细节与渲染几何在后段计算。灰稿的 x/y 像素不是另一套手工布局真源。

冻结的是内容与布局语义：页序、目的、主题句、分组、角色、主次、块顺序、必要关系、表达需求、区域归属和槽位语义。home 可以在相同归属与版式边界内测量和调整字体档位、间距、局部几何、颜色与装饰。跨越已声明容量时返回缺口；改分页、归属、关系或绑定需由 main 修订后重新冻结。

Skin/风格及允许的变体作为 home 编译请求与资产规则输入。完整 styleEnvelope 以实际资产声明为准，本提案不凭空给所有结构添加同一份样式范围。

## 冻结、检查与修订

- `contentSha256 = SHA256(canonical({origin,sources,plan}))`。
- `bindingSha256 = SHA256(canonical({canvas,pageBindings}))`。
- canonical：对象键递归按字典序排列，数组保留顺序，无空白 JSON，UTF-8；实现见 [检查工具](../../src/tools/validate-gray-handoff.mjs)。
- Schema、引用、来源和已有能力样例检查通过，只说明提案可解析。进入 frozen 还须完成合法候选、真实容量、内容覆盖和灰稿编译检查；审阅结果记录在 manifest/回执中，humanReview 可以 pending，不能写成用户已接受。
- manifest 中 program、semantic、humanReview 分别记状态，并引用本包 ID/revision/两个指纹；旧回执不能附到新修订上。更改交接内容后升 revision、回到 draft、更新指纹并重新编译。
- 编译器/能力变化、容量失败、导出或字体错误回 home；内容、关系、分页和绑定语义错误回 main。缺口回执至少包括 pageId、sourceLocation、失败责任点、原因与需要的能力。

现有 `planContentFingerprint` 为审稿复用服务，未覆盖完整交接字段；不直接拿它代替以上冻结指纹。

## main / home 本轮需要对齐的事项

1. main 能否导出上述包，并保持 gray-plan-3 的来源、限定、共同说明和阅读顺序。
2. layoutId/candidateId 如何落到稳定、可回放的版式 ID/参数；MVP 采用哪些真正可用的一级版式。
3. 结构在 main 冻结时选到具体资产/变体，还是只冻结槽位语义、由 home 从等价合法候选中选；本提案先采用前者，换资产需新绑定修订。
4. 块内图示、跨组关系、图表/媒体和多个局部结构的最小字段与当前支持边界。
5. 第一份共同样例用哪份真实灰稿，冻结检查在哪里执行；模拟包只证明后段，不能替代 main 语义验收。

## 后续模拟方式

先生成明确标记 `origin.kind:"simulated"` 的来源与契约，填写同样的正文、版式、表达、参数和槽位绑定。然后按同一编译器生成模拟灰稿；home 消费该包生成成品。每次保留契约、指纹、灰稿、成品和问题回执，不分别手工制作“看起来对应”的字段和灰稿。

[字段例子](examples/gray-handoff-v0.1.example.json)含文字页和成熟度阶梯页，仅用于对照字段、绑定与已有组件输入，不是已生成或已审阅的模拟灰稿。
