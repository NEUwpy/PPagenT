# 0930对谈：用前置设计与参数化能力可靠生成 PPT

整理日期：2026-09-30。依据[原始对谈](20260930对谈-可靠生成与参数化页面编译.md)梳理，保留讨论的主要问题、推理过程和最终边界，合并口语重复。下文 Q 为用户想法与问题，A 为对谈中的回应与建议。本文记录方向讨论，不代表相关接口已经实现、模型能力已经验证或项目已经通过验收。

## 一、要做的产品：给我一篇稿件，稳定地生成符合要求的 PPT

**Q：我现在最想确认的是，这件事到底可不可行，能不能继续推进。**

现在 Codex 等 AI Agent 已经能生成 PPT，但如果没有事先设置组织标志、页面样式、字体字号和制作规范，让它一次生成我想要的结果仍然很困难。我的第一步设想，是把这些要求提前规范好。

这里有两方面：一方面用 Skin 规定标题栏、标志等页面外壳；另一方面规定内容区的字体、字号、标题形式和页面组织规则。内容可以变化，但制作要求要有明确边界。这样至少能让 AI Coding Agent 做出符合我要求的 PPT。

但我的目标还不止于个人使用。我想把它做成产品：别人给我一篇稿件，我能稳定、可靠地把它变成 PPT。长期由我替别人操作 Codex，并依赖昂贵模型来完成制作，不是我想要的产品形态。

**A：这需要把制作能力拆开，提前收住可以确定的部分。**

先规定视觉身份和制作规范，可以减少每次生成时的不确定性。进一步产品化时，需要让成本较低的模型承担范围明确的工作，把可以复用的设计能力沉淀到系统中。

这条路线的出发点，是缩小每次生产时需要模型临场解决的问题，使输入、输出和制作过程更可控。它是否能达到要求，仍需要实际验证。

## 二、能力怎么分工：模型理解内容，系统复用设计

**Q：我的想法是，让 DeepSeek 这类模型负责语义理解和 PPT 内容规划。**

它需要理解稿件，判断哪些内容适合放在同一页，并识别这一页大致的逻辑关系。这些工作是否可以由成本较低的模型完成？

后面的页面组织、结构图和示意图，如果我提前有储备，把它们做成可以调用的组件库，就不用每做一份 PPT 都重新画一遍。我认为，临时设计和绘制这些表达，才是原来最考验高级 Agent 智能的地方。

**A：可以把已有设计的调用变成选择和填充。**

模型先理解内容，再判断应该调用什么表达能力。结构图的设计方法和绘制实现提前做好，生产时使用已有能力，减少现场创作的负担。

这里的关键分工是：模型负责理解、判断和选择；系统保存专业设计能力并执行制作。DeepSeek 这类模型能否稳定完成前面的工作，是需要验证的能力假设。

## 三、为什么要参数化：避免为每一种内容组合另做模板

**Q：组件库也有适配问题。提前做好的结构是四项，实际稿件只有三项，怎么办？**

只变化一个数量，也许还容易处理。但如果同时变化内容数量、文字长度、方向和其他条件，需要考虑的组合就会很多。固定模板会不会越做越多，最终仍然难以覆盖真实稿件？

**A：对谈中的建议，是把结构做成参数化原型。**

例如，一个并列结构可以定义支持的项目数量范围，并根据实际数量和内容量计算间距、方向等参数。四项变成三项时，调用同一个原型并改变参数，而不必重新设计一张模板。

对谈中用“支持二到六项的并列结构”举例说明这种思路；这个数字只是示例，并非项目已经具备的支持范围。超出原型适用范围时，需要选择更合适的能力。

**Q：那么，这可以叫作结构图的组件化、参数化。使用时相当于选择组件，再填参数。**

**A：对。** 可以确定计算的参数由程序计算；需要判断的部分，让模型在限定范围内选择或填写。这样可以把每次制作中对高级模型的依赖，转移为前期对组件、参数和程序的建设。实际能降低多少成本、覆盖多少情况，还需要用生产结果验证。

## 四、从讨论中提炼出的设计原则

**Q：我想把这些想法提炼成精炼的原则，作为之后做项目的依据。**

**A：对谈中归纳了六条原则：**

1. **固定的东西资产化。** 将可复用的制作要求和设计经验提前保存下来。
2. **能组件化的，不要每次临时生成。** 已有表达能力通过调用复用。
3. **能参数化的，不要为每种变化另做固定模板。** 用原型及其适用范围承载变化。
4. **能由程序确定计算的，不要让模型每次重新推理。** 把确定性的工作交给程序。
5. **尽量把生成问题转化为选择和填充问题。** 缩小生产时模型需要处理的开放空间。
6. **让复杂度沉淀到系统中。** 通过资产、参数、约束和实现积累能力，减少对长提示词及临时模型推理的依赖。

这些原则指向同一个方向：前期投入专业设计与工程建设，让后期生产能够以较低成本完成理解、选择、填参和求解。

## 五、拿到一页稿后，怎样决定页面组织

**Q：即使已经有了一页内容稿，我仍然困惑：这一页应该怎么组织，才能排得比较好？**

**A：对谈中提出，在内容稿与页面构图之间明确页面编排规划。**

先弄清楚这一页要让读者看懂什么、核心表达是什么、哪些内容是主、哪些是次，以及它们之间有什么关系，再决定用什么布局承载。

同样有四块内容，关系可能是并列、总分、对比或过程。内容块数量可以帮助判断容量，但不能单独决定页面组织。布局选择首先要依据逻辑关系和主次。

这一层要把内容的表达需求讲清楚，后面的参数化布局能力才能据此工作。需要包含哪些信息，仍有待进一步定义；本次对谈没有给出完整字段规范。

## 六、模型输出不完整时，整条流程怎样继续

**Q：从稿件到一页稿，应该输出什么格式？模型未必严格按照提示词填写字段。**

如果某次少了字段，是不是整页就断了，只能重新生成？如果字段已经给好，又怎样让 JEV 这类只做判断和选择的模型，据此选择大的版式、内部版式，以及哪些区域需要结构图？

**A：对谈中的建议，是把模型原始输出和系统内部的稳定表达分开。**

模型负责提出语义结果，程序负责解析、规范化和校验，再形成下游可以使用的标准对象。缺少必要信息时，针对缺口补充，而不必把已经有效的内容全部推倒重来。

进入页面决策时，可以把判断组织成有限选项：这页需要怎样的表达关系、采用什么主构图、哪些部分需要结构图等。具体判断的顺序、候选来源和接口，本次尚未确定。

对谈将最小的稳定页面内容对象暂称为 `PageContent`。这个名称用于说明中间契约的作用，不表示项目已经确定采用这个新对象或文件格式。

## 七、“编译”具体意味着什么

**Q：大语言模型应该先生成怎样的内容？普通程序又怎么把它编译成严格表达？**

**A：对谈中提出半结构化输出与容错编译的思路。**

先让模型回答核心表达、内容单元、角色、重要性和相互关系等语义问题，把布局、坐标和结构图外观留给后续环节。程序随后进行解析、规范化、枚举映射与校验。

如果某个必要关系没有给出，可以发起一个局部修补请求，让模型只判断这几个单元之间的关系。完成后检查必要字段、合法取值和引用，形成稳定的下游输入。

这是一项工程建议，本次没有给出解析规则或证明其可行性。尤其是，程序检查字段、枚举和引用，并不能替代对内容含义及逻辑关系的判断；原对谈中“程序发现几个单元是并列”的例子，也没有说明程序如何可靠地识别这种语义。因此，如何区分可由程序补齐的缺口与必须交还模型判断的缺口，仍未解决。

## 八、明确生产边界：只有两类模型，追求可靠生成

**Q：我想严格限定整个系统中起作用的模型类型。**

第一类是 DeepSeek 这样的语言模型，负责语义理解和逻辑分析，包括分页、内容规划，以及必要的语义和逻辑改写。第二类是 JEV 这样的模型，只负责判断和选择。生产中不再考虑更高级模型或 Codex 兜底。

我希望同一稿件生成十次，九次都能得到基本一样的样式。可以接受少一些临场创造性，再通过前期设计师和 PPT 制作者的劳动，建设丰富、好看的结构图，覆盖更多逻辑关系。

我对用户需求的判断是：很多人希望得到样式不错、逻辑清楚、能用结构图或框架图把事情讲明白的 PPT。我希望产品可靠地交付这个质量区间。

**A：这使产品目标集中到受约束、可复现的 PPT 生产。**

前期设计资产提供质量与丰富度，生产阶段以受限判断和参数化执行获得稳定结果。对谈用“语义可以智能，决策必须受限”概括这一方向。

“十次有九次基本一样”是用户明确表达的稳定性目标。对谈建议进一步考察核心表达、结构类型、布局家族和几何参数的一致性，但本次尚未定义“基本一样”的正式判据，也没有实际重复生成证据。

两类模型的分工是用户提出的生产边界；JEV 的具体型号、接口和能力没有在本次核实。此前助手曾提出复杂情况可使用更强模型兜底，用户在这里明确收紧了范围，整理版以这一后续要求为准。

## 九、这是否让项目更可行

**Q：按这个方向，做成这件事的可能性增加了多少？**

**A：对谈认为，这使项目更值得进行工程验证，但没有给出成功概率。**

需要检验的重点逐渐明确：前置的设计能力能否适配真实内容，页面表达契约能否稳定形成，有限选择能否选对，以及程序能否持续产出合格页面。

对谈建议，用少量参数化原型和稳定的页面表达，检查能否覆盖一批真实页面。“30 到 50 个真实页面”是助手给出的验证规模建议，没有在本次被确定为正式里程碑。

方向更清楚，不等于路线已经跑通；资产覆盖、语义判断、适配能力、成本和稳定性仍要由实际产物证明。

## 十、最后收敛为两个核心问题

**Q：接下来其实就是两件事。**

第一，从文稿能不能形成严格、参数化的页面表达？第二，从这个表达能不能稳定渲染出符合我要求和风格的 PPT 页面？

**A：对谈把它们概括为两个编译问题：**

| 问题 | 要验证的结果 |
| --- | --- |
| 文稿 → 严格页面表达 | 对稿件的理解、分页、内容组织和必要关系，能够形成稳定、可用的下游输入 |
| 严格页面表达 → 合格 PPT 页面 | 给定表达后，已有设计能力与程序能够稳定生成符合风格及表达要求的页面 |

两段可以分别验证，再检查完整流程。对谈建议先选两三种常见页面，例如结论—支撑页和并列要点页，反复走通文稿到最终页面，观察质量与一致性。这是下一步验证的建议，尚未成为已实施或已验收的结果。
