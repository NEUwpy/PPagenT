你现在这个状态已经很清楚了：接下来不要继续扩结构库，也不要继续磨“麦肯锡排版提示词”本身。下一阶段应该把“页面导演”做成正式中间层。

你现在真正缺的不是规则，而是一个可执行的 PagePlan 合同，把“内容语义”和“实际几何布局”之间接起来。这个 PagePlan 一旦稳定，结构、图表、文字才真正能进入同一个排版系统。

我建议你下一步就集中做三件事：PagePlan v1、统一局部表达接口、Occupation Map 占用模型。

一、先把 PagePlan 做成正式生产接口

你现在的 composition-intent 可以继续保留，但我会把它升级成类似这样的东西：

page_plan: page_id: P3 thesis: text: "本页最终要让读者记住的判断" source_group_ids: [g8, g9] reading_order: - g1 - g2 - g3 - g4 - g5 hierarchy: primary: g3 secondary: [g4, g5] supporting: [g1, g2] boundary: g9 must_coexist: - [g3, g4] - [g3, g5] optional_coexist: - [g7, g8] groups: - id: g3 original_text: "..." semantic_role: primary_evidence importance: primary preferred_media: - structure - text min_capacity: chars: 80 width: 420 height: 220 compressibility: low movable_to_notes: false - id: g4 original_text: "..." semantic_role: interpretation importance: secondary preferred_media: - text min_capacity: chars: 100 width: 260 height: 120 compressibility: medium movable_to_notes: false page_zones: - id: hero semantic_role: primary_visual preferred_share: 0.52 - id: insight semantic_role: explanation preferred_share: 0.28 - id: evidence semantic_role: proof preferred_share: 0.20 fallback_policy: on_capacity_failure: - try_alternate_media - recompose_page - split_page forbidden: - shrink_below_min_font - delete_condition - silently_rewrite_group 

这里最重要的是三件事。

第一，PagePlan 不应该只描述“有什么内容”，还要描述“谁必须和谁一起出现”。

第二，必须描述哪些内容不能牺牲。

第三，必须告诉后面的布局器：

容量不够时允许干什么，不允许干什么。

否则最后还是会回到：

放不下 → 缩字体 → 压成便签 → 截掉一句。

二、把 text / table / chart / structure 真正统一

你现在四种东西虽然概念上都是“表达媒介”，但代码入口还不统一。

我觉得下一步最关键的抽象就是一个统一的：

ExpressionAdapter 

所有媒介最终都接受同一种输入、返回同一种结果。

比如：

interface ExpressionRequest { groupIds: string[]; content: ContentGroup[]; role: SemanticRole; medium: | "text" | "table" | "chart" | "structure"; targetFrame: Frame; skin: SkinContext; visualGrammar: VisualGrammar; constraints: { minWidth?: number; minHeight?: number; maxWidth?: number; maxHeight?: number; preserveOriginalText: boolean; allowSummarization: boolean; }; } 

然后统一返回：

interface ExpressionResult { objects: RenderObject[]; occupiedShape: OccupationMap; textConsumed: { groupId: string; coverage: number; }[]; preferredAnchors: AnchorPoint[]; exclusionZones: Shape[]; attachmentZones: Shape[]; minimumReadableScale: number; actualFrame: Frame; diagnostics: { density: number; visualMass: number; overflow: boolean; }; } 

这样以后布局器根本不需要知道：

“这是漏斗结构。”

它只需要知道：

“这个表达结果真实占用了哪些地方，哪些地方不能放文字，哪些地方适合贴解释。”

这一步是你系统架构真正统一的地方。

三、你的“Occupation Map”不要一开始就做得特别复杂

你说真实占用轮廓，我完全同意。

但我提醒你一个坑：

不要一上来做像 CAD 那种像素级多边形碰撞系统。

那很容易做成无底洞。

你的 PPT 排版其实不需要那么精确。

我建议 v1 只做四种区域：

1. HARD 绝对禁止其他内容进入 2. SAFE_MARGIN 可以靠近，但不能进入 3. SOFT 允许少量文字进入/覆盖 4. ATTACH 推荐放解释、数字、注释的位置 

比如一个漏斗：

┌────────────────────────────────┐ │ ATTACH │ │ ↓ │ │ ┌───────┐ │ │ / HARD \ │ │ / \ │ │ / HARD \ │ │ / \ │ │ └───────────────────┘ │ │ SAFE_MARGIN │ │ ATTACH │ └────────────────────────────────┘ 

不要只返回：

{ "x": 100, "y": 200, "w": 600, "h": 400 } 

而是类似：

occupation: bbox: x: 100 y: 180 width: 620 height: 410 hard_zones: - polygon: [...] safety_zones: - polygon: [...] attachment_zones: - side: right y_range: [220, 350] preferred_for: - explanation - metric - side: top preferred_for: - title - annotation 

这已经足够让 PPT 排版产生质变。

但是我认为还有一个非常关键的调整

你刚才有一句：

“结构返回真实占用轮廓，然后布局器把剩余区域交给普通文字排版。”

这句话方向基本对，但我建议你再改一点。

不要理解成：

结构先落地 → 算剩余空间 → 文字进去。

最好是：

PagePlan 先产生区域意图 → 结构试排 → 反馈占用 → 全页二次求解。

也就是：

PagePlan ↓ initial region allocation ↓ structure/chart dry-run ↓ return occupation map ↓ global layout solve ↓ text + structure + chart jointly placed 

这里的关键词是：

dry-run。

结构组件第一次不要直接生成最终对象。

先做：

measure() 

类似浏览器 CSS 布局里的测量阶段。

比如：

structure.measure({ content, targetFrame, skin }) 

返回：

preferredSize minimumSize occupationMap visualMass anchorZones 

然后整页 Layout Solver 再决定：

“好，这个结构实际只需要左侧 56%，右侧可以放 explanation。”

之后才：

structure.render(finalFrame) 

这比“先把结构真的画出来再处理”稳定很多。

所以你的局部组件应该都有两个阶段

不是：

invokeUniversityStructure() 

直接画。

而是：

measure() render() 

最好所有 Expression 都这样。

例如：

TextExpression.measure() ChartExpression.measure() StructureExpression.measure() TableExpression.measure() 

然后统一：

LayoutSolver.solve() 

最后：

Expression.render() 

这就很像浏览器排版：

内容 → measure → layout → paint 

我觉得你现在的系统特别适合借这个思想。

四、Layout Solver 不需要一开始搞“AI 自由布局”

你现在已经有 resolveComposition / buildComposition，我反而建议这一层尽可能确定性。

Agent 负责：

这个内容组是主证据 这个应该用结构 这两个解释应该在它旁边 这个数字应该靠近对应证据 

Layout Solver 负责：

左 58% 右 36% gap 6% 组件 hard zone 在这里 右上 attach zone 可放 metric 右下可放 explanation 

换句话说：

Agent 决定语义关系，代码决定几何约束。

不要让大模型同时决定：

x = 426 y = 271 w = 351 h = 212 

这通常就是失稳来源。

五、你下一次测试页要专门挑“最容易把系统搞崩”的页面

不要继续测纯文字。

也别找一个特别漂亮、特别空的例子。

你下一张 benchmark，我建议强制包含：

1 个核心结构 + 1 组定量数据 + 1 个结论 + 2 组解释 + 1 个边界/条件 

类似：

页面主题句 ┌──────────────────┬──────────────┐ │ │ 核心结论 │ │ │ │ │ Structure │ 42% │ │ │ 定量证据 │ │ │ │ │ ├──────────────┤ │ │ 解释 A │ │ │ 解释 B │ └──────────────┴──────────────┘ 证据边界 / 条件 

但千万别把这个布局写死。

你让系统决定：

Structure 是 hero 还是 supporting？

如果结构只是解释性的，也可以变成：

主题 核心结论 + 数据 --------------------- 解释 Structure 解释 --------------------- 边界 

你真正要测的是：

PagePlan 能不能根据内容逻辑决定结构应该占据什么地位。

而不是测它会不会调用结构库。

六、这一阶段我建议先暂时冻结这些事情

这个很重要，不然项目很容易发散。

接下来一个迭代里：

先不要：

大规模增加新结构；

再造新 Skin；

加更多“风格词”；

继续修改标题字号之类细节；

做特别复杂的多边形碰撞；

让 AI 自己发明几十种 Composition。

优先顺序就是：

PagePlan → Expression Contract → Measure → Occupation Map → Global Solve → Visual Review。

我认为你的 v1 正式生产线最终应该长这样

Raw Manuscript ↓ Content Grouping ↓ Stable Content Groups ↓ PagePlan │ ├─ thesis ├─ hierarchy ├─ relations ├─ reading order ├─ coexistence rules └─ candidate media ↓ Expression Selection ↓ ┌──────────────────────────────────┐ │ text / table / chart / structure │ └──────────────────────────────────┘ ↓ Expression.measure() ↓ Component Contracts │ ├─ min size ├─ preferred size ├─ visual mass ├─ occupation map └─ attachment zones ↓ Global Layout Solver ↓ Final Frames ↓ Expression.render() ↓ University Skin ↓ Visual Critic ↓ PASS 或 RECOMPOSE 

这个时候你整个系统的核心就不再是：

AI 会不会做 PPT。

而变成：

AI 做页面决策，设计系统约束执行，布局器负责求解。

这会比继续磨 Prompt 稳定得多。

另外我还建议你增加一个概念：

PagePlan 和 RenderPlan 分开

这是非常值得做的。

PagePlan 是语义层：

谁重要 谁和谁相关 谁用什么表达 必须保留什么 

RenderPlan 才是几何层：

g3 → frame A g4 → frame B structure S1 → 560×410 metric → anchor right-top 

这样以后出问题特别好查。

比如你看到一页做丑了，你可以直接判断：

是 PagePlan 判断错了？

还是：

PagePlan 对，但是 Layout Solver 排错了？

还是：

Geometry 都对，但是 Skin 渲染得不好？

这对 Agent 系统调试非常重要。

所以如果让我替你定下一步开发任务，我会把它压缩成一句：

停止扩充表现能力，把 P3 的“先分组、保真实文、再选媒介”正式化为 PagePlan，并让所有局部表达支持统一的 measure → occupation → render 协议，再由全页 Layout Solver 做一次联合求解。

这应该就是你现在最值得做的主线。
