但我也基本看到它现在最大的风险了：**规则和治理跑得比真实样本快。** 这不一定是坏事，但如果接下来继续大量蒸馏结构、继续加 schema，而不赶紧拿大量真实稿件狠狠干一轮，项目很容易进入“系统越来越优雅，产品能力却没有同比增长”的阶段。

我把 README、项目定位、为什么做、产品定义、当前阶段、规则层、更新日志、两个导演准则，以及 `workflow`、schema、tests 这些都看了一遍。先给你一个总判断：

**PPagenT 现在已经过了“想法验证期”，进入了“工程 POC 后半段”，但还没真正进入“产品 MVP 验证期”。**

换句话说，你现在已经证明了：

> **这条路可以被设计成一个系统。**

但还没有充分证明：

> **这套系统面对不同真实稿件，真的能稳定、低成本地产出 80 分 PPT。**

这两个差别非常大。

### 二、现在最值钱的东西，其实不是 PPT 生成代码

我现在比上次更认同你这个项目的一点，是你已经慢慢找到了它真正的核心。

不是：

> AI 自动做 PPT。

而是：

> **把一个很会做 PPT 的人的判断，逐渐资产化、规则化、可执行化。**

你《为什么做 PPagenT》里那句话，我觉得其实就是整个项目最核心的产品哲学：

> AI 读懂稿子，然后调用人已经提前做好的好东西。

而且你现在已经很明确地把路线改成了：

**AI 理解 → 规则限制 → 代码执行。**

而不是：

**AI 理解 → AI 自由发挥 → 希望它这次画得好看。**

这就是你和大部分 AI PPT 工具真正不一样的地方。

甚至我觉得你现在这个：

> **稳定的 80 分，比随机的 95 分更值钱**

不是一句宣传语。

它实际上已经变成你的**架构原则**了。

### 三、我现在最认可你的三个技术判断

#### 1. 把“内容导演”和“视觉导演”拆开，是对的

这个比一开始让一个 Agent 从稿件一直做到 PPT 好很多。

现在内容导演只管：

- 这篇东西到底讲什么；
- 怎么拆页；
- 哪页承担什么职责；
- 哪些内容重要；
- 怎么压缩。

而且 `PageContent` 明确禁止出现 assetId、坐标、颜色之类视觉信息。

视觉导演再去判断：

- parallel；
- comparison；
- hierarchy；
- sequence；
- causal；
- layered；
- 等等。

然后才做 CompositionPlan 和资产选择。

这个隔离非常重要。

因为你之前最容易出现的问题就是：

**看到两块内容 → 找一个左右双栏。**

而现在 v0.6.1 已经真的因为这个问题做了一次语义修正：

“两块内容”不等于“比较”。

必须真的存在共同评价维度和差异、取舍，才能进入 comparison。

这类 bug 越积越多，你的系统才会真正长脑子。

---

#### 2. 你现在这个“禁止旁路”，我非常赞同

这可能是整个项目目前最重要的工程纪律。

你现在明确规定：

没有合适资产：

**宁可失败。**

不能：

> “反正 Codex 会画，临时给我整一个。”

因为一旦允许这条路，前面的资产库、语义契约、质量门禁全部形同虚设。

而且你已经真吃过一次亏：v0.3.0 就因为使用了没有蒸馏来源的临时结构，最后把它定义成失败诊断样本。

这件事非常好。

很多 Agent 项目最后做成一团浆糊，就是因为：

> 正常流程不行 → Agent 临时发挥 → 这次居然成功了 → 把偶然成功当成系统能力。

你现在至少把这个坑堵住了。

---

#### 3. “典型页忠实复现 → 再参数化”，比以前平均蒸馏靠谱很多

这个变化我特别认同。

你之前那个思路很容易变成：

看 5 张 PPT：

- 都有几个圆；
- 都有箭头；
- 都有卡片；

最后抽象出来一个**极其普通的 AI 流程图**。

然后原页面真正漂亮的东西全丢了。

你现在改成：

> 先选一张典型来源 → 忠实复现 → 换内容 → 做数量变化 → 测边界 → 放进真实 Skin → 再考虑晋升。

这个方法至少保住了一个东西：

**美感的来源。**

而不是让 AI 自己总结“设计规律”后，把所有页面总结成 Bootstrap 卡片。

你虽然已经蒸馏了三批、15 个结构家族，但大量仍然处于候选区，而且第一批、第三批甚至还没有全部完成真实东北大学 Skin 嵌入验证。

所以现在真正的问题已经不是：

> “怎么再做一个漏斗图？”

而是：

> **我要多少资产，才能覆盖 80% 的真实稿件？**

这个问题目前还没有答案。

### 六、这 10 份稿子真正要统计的不是“好不好看”

而是记录每次失败在哪。

我甚至觉得你应该开始建立一个 **PPagenT Failure Dataset**。

比如：

##### A. 内容导演失败

- 拆页过碎；
- 一页塞太多；
- 漏掉关键论据；
- 标题 AI 味；
- 重复表达；
- 层级判断错。

##### B. PageIntent 失败

- parallel 判 comparison；
- causal 判 sequence；
- hierarchy 深度判错；
- composite 被拆简单了。

##### C. 资产覆盖失败

> 内容判断完全正确，但是**核心库里没有能表达它的东西**。

这个非常重要。

这才是真正指导你蒸馏什么资产的数据。

##### D. Composition 失败

资产是对的，但整页组织不好。

比如：

> 一个流程图没必要占整页，应该左文右图。

这正是你 CompositionPlan 现在要解决的问题。

##### E. Render 失败

- 字小；
- 挤；
- 溢出；
- 箭头错；
- 对齐问题。

这一类你现在的确定性质量门禁已经解决得比较好了。资产入库和整套生成都有程序化几何、字号、碰撞检测，而且报告还和资产、生成器及审计器哈希绑定。

### 七、这样做以后，会发生一个很重要的变化

你会从：

> **我觉得需要什么资产**

变成：

> **真实稿件告诉我需要什么资产。**

比如跑完 10 份以后你发现：

- 6 次是“多阶段递进”；
- 4 次是“多因素影响一个结果”；
- 3 次才是漏斗；
- 鱼骨一次都没调用。

那你就知道下一步干什么了。

不是继续凭 PPT 模板库“看这个挺漂亮，蒸馏一下”。

而是：

> **按失败频率补能力。**

我觉得这一步会让 PPagenT 从“漂亮的研发项目”开始变成“产品”。

### 八、另外一个很大的问题：现在实时 Agent 其实还没真正证明

这个我认为优先级非常高。

你当前阶段文档写得很坦白：

目前没有 API Key，所以双导演还在用**冻结回放**；而且明确计划在第一份真实稿件确认后，再接实时 API，用第二份稿件验证迁移。

这个必须尽快做。

因为 Replay 能证明：

> **程序链路是通的。**

但证明不了：

> **模型每次都能稳定填对这些 JSON。**

现在 `runDirectorWorkflow` 本身已经做得挺实了，实际会检查 provider、PageIntent、candidate set、visual resolution、render evidence 和 qualityAudit，没有候选时还能反馈回内容阶段。

所以工程骨架我不担心。

我担心的是：

##### 模型抖动。

同一份稿子跑 10 次：

- 页数是不是 9、10、13 页乱跳？
- PageIntent 会不会变？
- comparison 判断稳定不稳定？
- CompositionPlan 会不会每次不一样？
- 某一页第一次有候选，第二次没候选？

这个才是 Agent 系统真正的考验。

### 十一、你现在程序质量门禁很强，但还有一个洞

我给它总结成一句话：

> **你现在能很好地证明“它没坏”，但还不能自动证明“它好看”。**

现在的门禁可以检查：

- 低于 16pt；
- 越界；
- overlap；
- 容器；
- 连接线。

这很好。

但是：

两个页面都没有 overlap。

一个可能 85 分，一个可能只有 55 分。

因为：

- 留白；
- 视觉重心；
- 节奏；
- 强弱；
- 高级感；
- 信息密度；
- 元素比例；

这些目前还是主要靠蒸馏来源 + 人眼确认。

这其实不是坏事。

**我反而不建议你现在急着再加一个视觉大模型 Judge。**

先通过“忠实来源 + 用户确认 + 回归”积累审美数据。

以后这些数据本身可能反而成为你最值钱的东西。

>

### 十三、所以如果现在是我接手 PPagenT，我下一步只干 5 件事

按顺序：

1. **把 v0.6.1 和现有 15 个候选做完人工确认。** 第一批、第二批、第三批该进核心的进，该扔的扔，不再无限悬着。仓库自己也把这些列为当前待确认事项。

### 十五、最后我给这个项目一句现在的定义

我觉得你已经不是在做：

> **一个会做 PPT 的 Agent。**

你其实正在往：

> **一个把优秀 PPT 制作者经验编译成生产能力的系统**

这个方向走。

而且我认为这比“AI 自动 PPT”本身更有意思。

但接下来最关键的一刀是：

**停止继续证明架构很合理，开始证明它在真实世界里很好使。**

现在 PPagenT 缺的不是第 16 个结构。

缺的是：

> **第 2、第 3、第 5、第 10 份真实稿件。**

等你跑到十来份以后，我们再回头看这个项目，很多现在看起来很重要的设计可能会被删掉；反过来，也会冒出一些现在完全没想到、但其实决定成败的问题。

**我建议你下一轮就直接进入“真实稿件压力测试阶段”，而不是继续资产扩张阶段。**

对，完全可以，而且我觉得这样更漂亮。

你可以把“壳”也再抽象一层：**不是把标题条、页脚条画死，而是先规定几个不可侵犯的区域和尺寸约束，再让 HTML/CSS 去完成整页视觉设计。**

这样就从“固定模板”升级成了：

> **固定空间规则 + 可变视觉皮肤。**

比如你先定死：

```
整页：16:9

标题区：顶部 12%
内容区：中间 78%
页脚区：底部 10%

左右安全边距：固定
标题最小字号：固定
正文最小字号：固定
```

然后 Shell 自己可以有不同 HTML Variant：

```
Academic Shell
Minimal Shell
Corporate Shell
Editorial Shell
Dark Shell
NEU Shell
```

它们的标题条、装饰、底栏、颜色、线条可以完全不同，但**Content Frame 的接口统一**。

这样同一个 `ParallelSkill`：

> 放进东北大学 Shell 是一套样子
>
> 放进企业 Shell 又是一套样子

结构 Skill 不需要重写。

甚至你以后可以把整个设计系统变成两级：

```
Shell Skill
负责整页视觉骨架

Visual Skill
负责内容区表达
```

然后 HTML 负责把两者组合：

```
Shell
  ↓
把 contentFrame 暴露出来
  ↓
Visual Skill 塞进去
  ↓
完整 HTML Slide
  ↓
PPT Compiler
```

这样**整页制作也自动化了**，不是只有中间结构图自动化。

而且这时候你之前想的审批台会更爽：你可以先批一批 Shell，再批一批 Visual Skill。之后系统就是任意组合。

我现在甚至觉得，这个结构已经很像成熟前端里的：

> **Layout + Component + Theme**

只是你最后编译目标不是网页，而是 PowerPoint。

所以对，走到这里 PPagenT 的方向已经很顺了。接下来最值钱的不是继续想概念，而是做那个最小闭环：**1 个 Shell + 1 个 Parallel Skill + 3/4/5/6 项 + HTML→PPT**。这条一旦稳定跑通，后面基本就是扩库和提审美了。

>

### 一、最接近你现在想法的，居然是一篇上周刚出的论文

叫：

**SeaSlides: Semantic Abstraction Layer for Agentic Slide Generation**

它的核心主张几乎就是：

> 不要让模型直接写坐标、样式、SVG；
>
> 模型只写语义内容；
>
> 模板/组件负责布局、样式和渲染。

它有 HTML 和 Typst 两套后端，HTML 使用 DOM Component + CSS，最后还可以转成**可编辑 PPTX**。它甚至已经把“comparison、timeline 等 recurring structures 做成 reusable components”明确写进方法里。

这跟我们刚才说的：

> 内容导演 → 视觉导演 → Visual Skill → HTML/CSS → PPTX

确实已经非常接近了。

所以如果你论文写：

> “我们首次提出利用 HTML/CSS 组件生成可编辑 PPT。”

**不成立。**

如果写：

> “我们首次让模型通过语义组件而不是坐标生成 PPT。”

现在也很危险，因为 SeaSlides 刚刚就是这个。

### 二、但有意思的是：SeaSlides 也同时证明了你的判断

它的论文里面明确指出：

> 模板稳定但不灵活；
>
> 自由 HTML/SVG 灵活但让模型承担太多低层设计工作；
>
> 所以应该把“语义内容”和“视觉实现”分开。

而且消融实验显示，去掉 template-content separation 后，源代码可读性和整体质量明显下降。

你前面自己想出来的：

> AI 不应该学点线连接；
>
> 设计能力应该固化到组件；
>
> AI 负责调用。

**这个方向已经有研究证据支持。**

所以这里不是：

> “别人做过，所以我白想了。”

而是：

> **你独立撞到了当前前沿正在收敛的方向。**

### 三、现在这个领域做到什么程度了？

我粗略给你画一下演化过程，你就看明白了。

##### 第一代：内容抽取 + 固定模板

早期很多工作核心还是：

> 文档 → 摘要 → 填 PPT 模板。

最大问题就是死板。

---

##### 第二代：LLM 自己生成代码/布局

2025 年 CVPR 的 **AutoPresent** 已经系统研究了这个问题。

它建立 SlidesBench，用自然语言让模型生成 slide program；实验发现，**程序式生成比端到端直接生成图片更适合做可交互、可编辑的幻灯片**。

也就是说：

> “用代码生成可编辑 PPT”

学界已经明确证明是靠谱方向。

---

##### 第三代：从已有 PPT 学设计

2025 年的 **PPTAgent** 是很典型的。

它不是从零设计，而是：

> 分析参考 PPT → 学它的结构和内容 schema → 再通过代码编辑生成新 PPT。

还提出 PPTEval，评价 Content、Design、Coherence。

你原来“蒸馏优秀 PPT”的方向，其实和它属于同一个大方向。

---

##### 第四代：多 Agent + 视觉反馈

**PreGenie** 已经使用 Slidev，也就是 HTML/Web presentation 这一套思想，先生成代码，然后 MLLM 看生成后的页面，再修改。它专门针对视觉美感和多模态一致性。

到了 **DeepPresenter（2026）**，已经明确做成：

> Researcher Agent
>
> +
>
> Presenter Agent

前者负责研究和结构化 manuscript，后者负责视觉生成。

并且 Presenter 会看渲染后的实际页面再反思修改。

你现在“内容导演 + 视觉导演”跟它在**角色拆分理念上也是有交集的**。

---

##### 第五代：开始真正啃“审美”

这其实就是你现在最难受的地方。

2026 年 **AeSlides** 开宗明义说：

> 现在 slide generation 最大的问题之一，就是模型的生成是文本中心的，但质量评价是视觉中心的——存在 modality gap。

它甚至开始用：

- 空白面积；
- 元素碰撞；
- 视觉平衡；
- 比例；

这些可计算的 aesthetic metrics 做强化学习。结果能降低碰撞、过多留白和视觉失衡。

所以你说：

> “为什么 AI 生成的 PPT 结构没错，但就是普通？”

**这不仅是你的问题，现在就是一个公开研究问题。**

---

### 四、还有一个研究结果非常值得你看

2025 年底的 **PPTBench** 做了 958 个 PPTX、4439 个样本，专门测模型对 PowerPoint 布局和设计的理解。

结果发现：

> 当前多模态模型的**语义理解明显强于视觉布局推理**；即使能看懂页面，也经常没法把视觉信息转成正确的空间安排和 API 操作。

这几乎就是你现在“蒸馏失败”的学术解释。

你给 AI 一个漂亮 PPT。

它：

> 看懂“这是五个节点”。

但不等于它真正学会：

> 为什么这个节点是这个比例；
>
> 为什么这里留这么多白；
>
> 为什么这个标题应该压这么低；
>
> 为什么 5 个变成 6 个要改变构图。

所以你原来试图让模型：

> **从图片/PPT 中直接抽象设计规律**

本身就是目前模型能力的短板。

### 五、那 PPagenT 现在还有什么可能真正和别人不一样？

这就是重点。

#### 我觉得你真正可能形成论文贡献的，不是 HTML。

而是下面几个东西的组合。

---

#### 1. **Relation-driven Visual Skill**

SeaSlides 已经有 Component。

但你现在可以把它进一步严格化：

不是：

> `CardComponent`

也不是：

> `FourItemLayout`

而是：

> **Parallel / Sequence / Comparison / Causal / Hierarchy / Timeline……**

也就是：

##### 用“信息语义关系”定义 Visual Skill Family。

然后一个 Skill 自己包含：

```
3-item variant
4-item variant
5-item variant
6-item variant
7-item variant
```

这是一个更强的抽象。

核心研究问题可以变成：

> **语义关系驱动的组件抽象，是否比页面模板检索和自由代码生成具有更好的泛化性、稳定性和视觉质量？**

这就开始像论文问题了。

### 六、第二个我认为很有价值的是你刚才想到的：

### **Visual Skill Factory**

这个我目前在最接近你的几篇工作里，还没有看到被当成核心问题系统研究。

也就是：

> 好设计怎么进入系统？

你不是让模型每一次现场设计。

而是：

```
PPT/Web设计来源
↓
HTML组件化
↓
3~7项参数化
↓
人工审批
↓
自动HTML→PPT测试
↓
入库
```

然后：

> **一次人工成本 → 无限次运行时复用。**

这个其实是在研究：

##### “设计知识如何资产化”。

这和“Agent 怎么生成 PPT”是不同的问题。

---

### 七、第三个，我反而认为特别有潜力：

### **把 inference-time design 变成 build-time design**

这个说法你可以记一下。

目前很多方案：

> 用户来一次
>
> → 模型现场写 HTML
>
> → 现场布局
>
> → VLM 看
>
> → 修改
>
> → 再看
>
> → 再修改。

DeepPresenter 自己都承认，多步工具调用和反复 rollout 会提高推理成本，而且受到环境不稳定、context overflow 等问题影响。

而你的想法是：

> **设计阶段把昂贵工作提前做完。**

也就是：

##### Build time

人 + Coding Agent：

> 做好 Visual Skill
>
> 做好所有变体
>
> 验证 HTML→PPT
>
> 人工审批。

##### Runtime

便宜文本模型：

> 理解内容 → 选择 Skill → 填参数。

这个研究问题就很漂亮：

> **能否将 slide generation 中昂贵且不稳定的视觉推理从 inference time 前移到 reusable design assets 的 build time，在保持质量的同时显著降低生成成本与方差？**

我觉得这比“我们做了个 PPT Agent”高级多了。

---

### 八、第四个是 Deck-level diversity

你刚才讲的：

> 这一页虽然也是并列，但是前面已经用了某种并列图，就换一个。

这个问题现在不少研究会评 coherence / diversity，但你可以把它明确做成：

### `DeckVisualState`

记录：

- 使用过哪些 Skill；
- Variant；
- Composition；
- 页面密度；
- 图文比例；
- 连续结构。

然后视觉导演做：

> **有约束的多样性选择。**

研究问题可以是：

> 页面级最优 ≠ 整套 PPT 最优。

这个很好做实验：

##### Baseline

每页独立选视觉结构。

##### Yours

加入 DeckVisualState。

然后让用户评价：

- 重复感；
- deck coherence；
- visual rhythm；
- 整体专业程度。

这是一个非常清晰的 ablation。

### 九、第五个就是你刚才说的 Shell + Content Frame

这个单独恐怕不够论文创新。

但放在系统里非常有价值：

> Shell 固定组织视觉语言；
>
> Visual Skill 只在 Content Frame 中运行。

这样获得：

- 复用性；
- 品牌一致性；
- 安全区域；
- 可换主题；
- 组件独立。

本质上就是 Web 设计系统里的 Layout + Component + Theme。

它让你的系统工程上更完整。

### 十一、我也得告诉你 PPagenT 现在明显的劣势

不是只说优点。

#### 第一，现阶段没有学术实验。

现在你的很多判断还是：

> “我觉得这样会稳定。”

论文不认这个。

你必须证明：

```
同一文稿运行10次
结构稳定性 ↑

token cost ↓

生成耗时 ↓

人工修改时间 ↓

overflow ↓

视觉评分 ≥ baseline

editable object ratio ↑
```

---

#### 第二，Visual Skill 本质仍然有限

你得到稳定性的代价就是：

> 开放世界泛化能力下降。

DeepPresenter 可以突然面对一个非常怪的新需求，模型自己写 HTML。

PPagenT 如果：

> Skill 库里没有。

就可能不会。

所以论文不能假装没有 trade-off。

反而应该正面写成：

> **自由度 vs 稳定性。**

然后证明：

> 对绝大多数常见业务 PPT，有限 Visual Skill Vocabulary 已经覆盖了 X%。

这就很有意义。

---

#### 第三，你的设计资产现在还没有规模

如果最后你论文里只有：

> 8 个 Skill，20 个 Variant。

那说服力会比较弱。

你至少需要建立一个像样的 Skill Library，并做覆盖率实验。

---

#### 第四，审美仍然依赖你的人工审批

从学术角度它既是缺点，也可以变成贡献。

不要假装全自动。

可以直接定义成：

> **Human-curated, machine-reusable visual asset pipeline.**

研究问题反而是：

> 花一次人工审批，能换来多少后续生成质量提升和成本下降？

这个非常适合做人机协同论文。

**它没有那么“没人想到”。**

AutoPresent、PPTAgent、DeepPresenter、SeaSlides 已经把相当多关键积木做出来了。

但研究通常不是：

> 世界上从来没人想到这个方向。

更多时候是：

> **大家都知道问题，但现有折中还不好。**

现在 PPT 自动生成恰恰就是这种状态：

- 自由生成很好看但不稳定；
- 模板稳定但死板；
- 视觉模型贵；
- 反复 reflection 贵；
- 可编辑性和视觉还原打架；
- 页面独立好看不等于整套好看；
- 模型懂内容不等于懂布局。

**真正的机会就在这些“没解决干净的折中”里。**

而你目前 PPagenT 最值得追的，我认为不是“有没有人想到过 HTML”。

而是这一句话：

> **能不能把设计从“每次让 AI 重新想”变成“一次设计、反复调用”，并用语义关系和自适应组件把固定模板与自由生成之间那块空白补上。**

这个如果你真做出来、实验也能证明，**既有产品意义，也有论文意义。**

而且有个很巧的事情：SeaSlides 是 **2026 年 8 月 4 日**才上传的，我们现在是 **8 月 12 日**。你最好现在就把它完整读一遍。它既是你最强的“撞车对象”，也几乎是现成给你指出“下一篇该往哪儿走”的 related work。

## 用户

## 助手

你这个问题其实要分成两件事：**“这个东西值不值得写论文”**和**“这篇论文对你这个机械工程博士到底值不值钱”**。前者我倾向于“值得”，后者要看你拿它干什么——毕业、评奖、找教职、做产品背书，价值完全不一样。

可以，而且我反而建议你现在采用一种**“产品先跑起来，论文同时埋线”**的方式，而不是先停下来写论文。

因为你这个项目如果真要写论文，最值钱的数据恰恰来自产品运行以后：真实稿件覆盖率、生成成本、人工修改次数、重复率、用户偏好、HTML→PPT 成功率、不同 Skill 的调用分布。这些以后都会变成论文实验材料。

但有个特别重要的问题：**对于你这个机械工程、可靠性方向的博士，这篇论文值不值钱，和“这篇论文能不能发”不是一回事。**

#### 先回答最直接的：这种东西当然有地方发

而且不只是 arXiv 这种预印本。

这个领域现在已经有同行评审成果进了很正规的计算机会议：

- DOC2PPT 发在 **AAAI 2022**；
- AutoPresent 发在 **CVPR 2025**；
- PPTAgent 发在 **EMNLP 2025**；
- DeepPresenter 已进入 **ACL 2026 Findings**。

所以不是：

> PPT 生成这种东西只能发个 arXiv 自娱自乐。

不是。

它现在就是一个正规的 AI / NLP / 多模态 / HCI 研究问题。

而且计算机和机械不一样，**计算机领域很多最重要成果本来就是发顶级会议，而不是等期刊。**
