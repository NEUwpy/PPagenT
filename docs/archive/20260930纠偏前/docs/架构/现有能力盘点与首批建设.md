# 现有能力盘点与首批建设

2026-09-28，基于本地合并后的 `main`（基准提交 `c81c6c60`）及当前工作区。本文是实现与证据快照，建设原则仍以[产品目标与路径](../产品目标与路径.md)为准，接口职责见[页面构成与布局规范](页面构成与布局规范.md)，任务状态只在[项目台账](../方向讨论/页面编排能力计划.md)维护。

本轮读取运行入口、资产声明、关键实现和已有产物，运行定向测试及最小接口探针；没有改生产代码、调用生成模型或重新生成整稿。原始清单、探针结果、测试日志和复现命令在[盘点证据目录](../../experiments/capability-inventory-20260928/README.md)。

## 一、结论及判断口径

已有来源管理、规划状态、文字测量、组合求解、结构构建和原生导出基础，值得继续使用。当前主要断点是：语义组与视觉块仍被绑定为同一个粒度，灰稿可选关系范围较窄，前后段表达契约不一致，美化仍由模型逐区设计。下一步应补这些连接及可调用的表达能力，而不是另建运行器或继续为单稿添加提示词。

盘点分别回答“已登记”“有实现”“正式入口可达”“有当前验证证据”。四者不能互相替代：`core` 不代表新适配路径已经通过，`awaiting-user-review` 不代表用户认可，看板 HTML 和手写实验不代表正式生成。

## 三、资产登记与实际成熟度

### 结构、布局和文字

- 当前 35 个 `core` 结构，均声明 `html-component`，覆盖 Logic 表中 20 类的 18 类；旅程、地域两类没有登记资产。35 个都有字段、容量、语义及空间声明，也都有示例 PPTX。声明存在不证明全部输入有效。
- 35 个结构的 guide 均登记 `preserved-design`；32 个为 `implemented-unreviewed / not-validated`，3 个为 `sample-verified-candidate`。三个是双排折角便签、简明转化漏斗、成熟度阶梯。旧文档“只有三个有实现”已不足以描述合并后的代码；“全部已验收”也不成立。
- [structure-skills](../../src/runtime/structure-skills.mjs) 的发现只要求元数据，不先导入实现；`executeStructureSkill` 既能接外部 build，也能走登记的 preserved-design。[preserved-structure-build](../../src/runtime/preserved-structure-build.mjs) 复用原 review 实现及原生编译，当前一次调用只处理一个参考结构。后半段灰稿通路已经使用这一模式，值得继续接入。
- [composition-layouts](../../catalog/composition-layouts.json) 有 14 个静态布局：3 个固定页、3 个组件布局、6 个 editorial 布局、2 个图文布局；[加载器](../../src/composition/layouts.mjs) 另加 `component-gray-regions`，共 15 项。视觉工具只开放 editorial/component 前缀，灰稿交接又强制保留灰稿区域；不能把 15 个全算成正式灰稿候选。
- [文字库](../../src/visual-runtime/text-layout-library.mjs) 当前公开两个候选 `markdown-flow / markdown-zoned`，均待用户审阅；另外十个旧定义仅留兼容。存在 HTML 文字排版程序，不代表正式灰稿或美化已经使用它；需验证测量与原生构建后再接入。

### Skin、风格与扩展 Skill

[规则索引](../../rules/index.json) 绑定东北大学→麦肯锡式、中性→杂志风；已有两个 Skin 的字体、色彩、正文区域及原生绘制配置，可复用。这不等于风格说明已经全部转为可执行参数：灰稿美化仍要求模型逐元素指定样式与位置。第一批先固定一个当前 Skin 验证，再换另一 Skin 检查角色约定，避免在多个风格中同时追外观。

Archify 与 Lieflat Charts 是按需使用的补充 Skill，项目接入说明要求继续完成原生转换/重建与整页验收；不能登记成已经自动可用的通用原生资产。图表 Skill 的本地说明注明非商业限制，本轮没有重新核验上游许可。商业适用性仍按实际依赖另行核对。

## 四、本轮核实的连接缺陷与基线问题

| 编号 | 事实与影响 | 下一步处置 |
| --- | --- | --- |
| G1 | 正式布局区域直接对应 group，组内并列条目不能独立成为视觉块；需要换排布时容易被迫改语义分组 | 复用人工映射原型，建立内容 ID→视觉块与 scope 绑定；接回原灰稿入口 |
| G2 | 候选容量先算，关系由模型在选择回包中报告；只对回包 relation 做支持性判断。可读关系不能由卡片数量证明 | 在同一计划契约中记录必要关系和适用依据，再筛可执行候选；不靠“把关系改成 parallel”获得候选 |
| G3 | `validateGrayRegionPlan` 拒绝 0 个和多个图示区，`build-tools` 的 component 也要求单 structure | 表达绑定支持 0/1/多个独立位置；按稳定 location 绑定，每区完整保留来源。与实际 renderer 同步迁移 |
| G4 | 最小探针显示 `kind:note` 被 `expressionRequirements` 当图示；`grayTextSources` 不返回 note，且只回填 block.text、不回填独立 label | 先统一“文字/标签/附注/结构说明”的定义，保留 label 与限定；不得为通过交接删 note 或改成图示。现象已复现，尚未修复 |
| G5 | 35 项适配实现的登记状态与证据强度不同；选择端发现资产不等于每个数量/尺寸通过 | 首批只对所需结构验证实际输入、数量、区域及 Skin；不批量晋升，也不重写所有 35 项 |
| G6 | 美化的 frame、字号和装饰仍是模型输出 | 先建设可测量的标题、正文、标签、附注与图区排布程序，模型选能力与合法变体；无需改写已有导出引擎 |

定向基线覆盖 11 个测试文件、51 项：43 通过、8 失败，原始日志完整保留。失败为：

1. `gray-regions` 一项：实际图示区域高度/位置与断言不一致，需要判断契约和期望谁正确，不能直接改断言求绿。
2. `preserved-structure-build` 一项：大学风格转换出现 `UNCOMPILED_VISUAL_NODE`，涉及 `note-card` 承载面。
3. `runner-build-tools` 六项：四项直接报告模板文本 `MDM方法偏移量自适应选取` 找到零个，另两项表现为 accepted 为 false 的断言失败；两项的内部原因未进一步确定，不合并猜测为同一根因。

这些是本机当前代码/资源/运行时组合的基线，未定位是否由模板资源、依赖版本或代码引起。已有历史成功产物不能覆盖当前失败。灰稿资产建设可以推进，成稿原生验收前必须处理实际阻塞；本轮没有扩大到全仓测试或修改基线。

**下一项开发任务确定为第 1 项：语义组到视觉块的映射，并把现有分组/共同说明能力接入同一个灰稿入口。** 第 0 项在接入成稿验证前处理；若其依赖影响灰稿导出则前移解决。第 2 项在映射稳定后扩关系覆盖，第 3 项消费同一绑定，不重新生成正文。

第 1 项的最小交付不只是 Schema：要有可调用程序、固定计划的多种内容与容量边界、原生 PPT/PNG、来源与作用范围核对结果，以及正式入口调用记录。人工核对计划作为程序建设输入，与模型自动规划结果分开保存。对于尚无能力的对照、因果和分支，要如实返回缺口，不能重标为并列来凑成功。

首批暂不建设完整语义图平台、新调度框架、全库自动迁移、缓存服务或更多同义提示词。它们不解决本次盘点确认的主要断点。后续只有覆盖证据出现新需要时再扩范围。
