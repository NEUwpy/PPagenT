1. 盘点现有流程、代码、资产和方案，对齐整体职责与交接。
2. 讨论前后段怎样编排、调用设计能力，明确模型、判断器与程序的分工。
3. 据此讨论运行方式、内部表示和 PPT 引擎，记录沿用、调整及选择依据。
4. 最后反推 Markdown 格式，形成后续建设范围；整体方案讨论清楚后才开始实现。

## 已确认的架构骨架

```mermaid
flowchart LR
    B[MD 与相关资源] --> C[前段：页内编排]
    C --> D[灰稿页面表达]
    D --> E[共享编译器]
    E --> F[灰稿预览]
    E -->|通过检查的同一份页面表达| G[后段：视觉制作]
    G --> H[可编辑 PPTX 与成品检查]
```

当前建设从 MD 开始，输入前提与材料适配范围以[目标与路径](产品目标与路径.md#当前责任markdown--pptx)为准。分支分工见[AGENTS](../AGENTS.md#分支分工)。

| 环节 | 职责 |
| --- | --- |
| MD → 灰稿（编排） | 理解内容，确定页内分组、主次、关系和阅读顺序；匹配页面版式、安排区域并绑定内容 |
| 共享灰稿编译器 | 校验页面表达与交接条件，生成可审阅的灰稿和诊断，检查前段产物是否符合后段消费约定 |
| 灰稿 → 成品（美化） | 按既定区域选择并调用结构图、放入图片，通过文本框或排版程序落实文字，应用样式并生成、检查 PPTX |

**灰稿确定内容与整页编排。** 文字、图片和图示的所属页、位置与面积在灰稿中明确；后段沿用这份编排，不重新分页或改变内容归属与关系。

**结构图在后段选择。** 前段把适合图示表达的内容描述、关系与要求放入蓝区，确定位置和面积；不选定具体资产或绑定其内部槽位。后段据此选择结构图，完成内部布局、内容适配和原生绘制，保持原意与关系。图片区域保留资源与放置要求，由后段放入图片。

灰稿以结构化页面表达为源，预览是编译视图。文字区呈现实文和层级，蓝区呈现制作描述与要求。后段读取同一份页面表达，不从预览图识别内容或布局。

## 设计能力与运行基础

两段流程调用已有设计能力，并共享运行与检查基础。这些能力怎样组合是本轮讨论内容，不预先要求新增框架或重建全部组件。

| 部分 | 在整体架构中的作用 |
| --- | --- |
| 页面编排能力 | 为前段提供整页分区、主次、对齐与图文组织方式 |
| 区域制作能力 | 为后段提供标题、文字、图文组合、结构图和图表等可复用实现 |
| Skin 与风格规则 | 提供身份素材、色彩、字体及设计约束；与两段流程的具体参与时机待讨论 |
| Agent 与确定性程序 | 模型理解内容、作受限判断与选择；程序处理测量、几何、绑定、能力调用和编译。具体模型与调用顺序待定 |
| 运行与检查 | 管理状态、上下文、工具调用、记录与恢复；分别检查来源语义、交接表达和最终 PPTX |

## 共享编译器与并行建设

两条建设线使用同一份灰稿规范和编译检查。后段可先使用符合规范的模拟灰稿，再接入前段真实产物；编译器是共同的交接检查依据。

编译检查需要覆盖：

- 页面、元素、关系和资源引用是否有效，内容与区域的绑定是否完整。
- 区域位置、面积、边界和必要避让是否满足编排要求。
- 文字区域及蓝区的表达是否符合交接约定，蓝区的内容描述、关系和要求是否齐全。

结构匹配及制作检查由后段完成；编译器的具体检查范围结合既有实现继续确定。

语义忠实与表达是否讲清楚，由语义审查和建设审阅判断；编译器检查交接表达。成品仍需检查实际原生对象和导出结果。

这是后续建设安排，当前不启动两线实现。
