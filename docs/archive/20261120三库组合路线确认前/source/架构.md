# 系统架构

本文维护现行架构分工、实现边界和可复用资源。产品范围见[目标与路径](产品目标与路径.md)，试验取舍见[技术选型与决策](技术选型与决策.md)。

## 已确认的骨架

```mermaid
flowchart LR
    A[Markdown 与来源资源] --> P[内容组织]
    P --> S[单页内容 JSON]
    S --> V[表达选择]
    V --> X[内部表达方案]
    X --> D[排版计算]
    T[主题的内容区与排版约束] --> D
    D -. 容量反馈 .-> V
    D --> L[经测量的布局结果]
    L --> E[灰稿预览]
    L --> F[Home：PPT 原生制作与样式应用]
    F --> G[可编辑 PPTX 与成品检查]
```

| 环节 | 责任 |
| --- | --- |
| 主题约束 | 提供内容区几何及影响容量的字体、字号和行距，灰稿可简化页壳 |
| 内容组织 | 从稿件确定每页主旨、实文、讲述备注、内容分组、语义关系、阅读顺序、限定的作用范围与来源 |
| 表达选择 | 依据内容关系选择文字、对照或图示，绑定实文并核对关系方向与限定范围 |
| 排版计算 | 按实文、内部表达方案与主题约束编排整页，测量真实文字和组件，输出布局结果、预览与容量诊断 |
| 灰稿 → 成品 | 按布局结果制作原生文字、图形及媒体，应用主题页壳与样式，检查可编辑性和实际 PPT 渲染 |

## 灰稿与交接

灰稿是完成主要表达与空间设计的整页制作蓝图。它显示真实文字、层级、选定组件及内部内容，排版尽量接近最终 PPT。灰稿可简化配色与装饰，保留影响占位的文字尺度、组件几何和空间分配。

正文页在主题页首先呈现主旨句，再呈现页题，正文从独立的内容区开始。正文以讲述与听众理解为目标，保留必要结论、关系和限定，展开论述可由讲述稿承担。

灰稿编译的公开 JSON 仅承载内容与语义关系。组件选择和内容绑定进入内部表达方案，尺寸、分区、换行等排版信息进入布局结果。原生制作接收同一布局结果及其中的组件绑定，灰稿预览供审查该次布局。

`page-content@1` 是本轮的内容接口试验格式。`gray-page-plan@1` 是已有独立编译器的内部计划，包含具体表达绑定。两者的实测见[技术选型与决策](技术选型与决策.md#2026-11-20-内容与编排试验)。

后段读取同一份布局结果，复用组件几何或其计算方法完成原生制作，不从截图反推位置，不另选表达或结构、重新分页或独立重排。原生实现问题修所属制作能力；确需改变内容、组件或布局时回写灰稿并重新编译。分支安排见[AGENTS](../AGENTS.md#分支分工)。

布局依赖内容区形状和排版条件，不仅是面积。主题变化影响内容区或文字占位时重算灰稿；HTML 测量与实际 PPT 换行、边界的差异须在成品中检查。

## 设计能力与检查

组件库提供文字、图文、流程图、结构图等可复用表达；调用时以真实内容、区域和排版约束测量容量，组件与整页布局共同调整。纳入制作的组件须核对 HTML 呈现与原生 PPT 实现的对应能力，共用设计边界与几何依据，不能以库登记或预览可用代替原生验证。

分别核对原文对内容的支持、表达对文字和关系的保留，以及排版的文字层级、容量、边界、避让与交接完整性。成品检查内容保留、原生对象、文字换行、连接与实际导出。具体检查深度待定。

结构或容量失败时，区分输入方案、可用组件和实际排版的问题，按报告返回对应环节。编译时保留原有文字和关系；确需调词或拆页时修订方案后重编。

## 实现边界与可复用资源

独立编译试验已能从单页方案生成真实组件灰稿。它在同一次浏览器测量中导出预览和布局，为交接提供可读数据。Markdown 自动规划、工作台接入、不同 Skin 和 Home 消费本轮布局结果待验证。下表中的已有代码按各自输入协议使用。[独立编译试验](../experiments/gray-compiler-20261120/README.md)

| 入口 | 核查到的能力与限制 |
| --- | --- |
| [工作台 main](../src/workbench/main-flow.mjs) | 已接入原稿读取与规范化。后续步骤只登记输入、输出与检查项，独立编译器尚未接入 |
| [既有灰稿 Agent](../src/runner/gray-agent.mjs) | 有语义计划、来源审查、布局测量选择、内容绑定及旧灰稿导出，可按入口复用 |
| [成品运行器](../src/runner/run.mjs)、[制作工具](../src/runner/tools/build-tools.mjs) | 可读灰稿并保留分区、调用结构与制作；当前交接仅支持零或一个图示区，部分文字仍由模型给几何 |
| [旧双导演](../src/agent/workflow.mjs)、[工具循环](../src/runner/loop.mjs)、[状态](../src/runner/state.mjs) | 两套调度并存；已有持久状态、参数校验、日志及 Chat/JEV 接入，保留哪些待定 |
| [灰稿候选](../src/runner/gray-layout-catalog.mjs)、[页面布局](../src/visual-runtime/page-layout-library.mjs)、[组合布局](../catalog/composition-layouts.json) | 七类灰稿程序覆盖并列、独立及部分主辅分带；另有 14 个静态组合布局，不能全部视为前段可用候选 |
| [既有灰稿导出](../src/runner/gray-draft.mjs)、[交接校验](../src/runner/gray-expressions.mjs)、[页面表达候选](../src/visual-runtime/page-expression-plan.mjs) | 各自使用预留区或具体结构 ID 等既有协议，提供可核查的兼容及迁移依据 |
| [文字库](../src/visual-runtime/text-layout-library.mjs)、[文字程序](../src/render/gray-text-program.mjs)、[内容映射](../src/runner/visual-block-mapping.mjs) | 有两个 MD 排版候选、纯文字 `source-text-v1` 及受限分组合并能力，尚未形成统一制作通路 |

| [Skin](../src/runtime/skins/)、[规则](../rules/)、[来源处理](../src/content/)、[选择器](../src/selection/) | 有东北大学／中性风格、来源绑定及内容和排版规则；按实际消费点核对复用 |

## 本次重议的依据

[9 月 20 日样例](../experiments/home-mckinsey-style-20260920/README.md)以用户生图为视觉参照，在固定灰稿上经多轮规则和代码调整生成原生 PPTX；具体过程见[当时记录](方向讨论/20260920.md)。它说明局部可以复现，跨稿自动交付仍未证实。

此前枚举组件、调灰稿与看图修改消耗较大。此次需同时判断：组件怎样组成好的整页设计，调整是否进入实际制作能力，迭代能否带来可复用的改进。设计效果、建设成本和复用收益都影响路线选择。

## 尚待明确的架构

- 哪些内容关系、组件和幅面可以稳定复用同一编译入口，怎样扩展回归样本。
- 如何将已整理的 Markdown 转成可靠的单页内容，哪些原稿歧义与表达取舍需要模型或用户判断。
- Home 如何消费实际布局，怎样核查 PPT 测量差异与处理失败回写。
