# PPagenT 适用性与视觉系统优化调研（历史归档）

> 本文记录 2026-08-24 的阶段性调研，资产数量和 VisualStructureIR 路线已经过期。当前判断见[方向校正](../../方向校正.md)与[正式生成线架构决策](../../工作流/正式生成/生成线架构决策.md)。

> 文档状态：架构调研稿  
> 调研日期：2026-08-24  
> 适用范围：Visual Scale、Structure Group、HTML Visual Skill、正式生成与资产入库流程

## 一、核心结论

PPagenT 不应继续主要依靠增加“完整结构图模板”来解决适用性，而应把有限的结构资产升级成一套可组合的视觉语法。

模板可以是有限的，但由语义图、布局算子、视觉样式和内容槽组合出来的实例可以很多。这样才能覆盖现实中无法穷举的结构，同时保留可靠、可审核、原生可编辑的产品边界。

下一阶段的重点不是推倒现有 HTML → 原生 PPTX 编译链，也不是立即建设更多孤立结构图，而是在其上游增加一个结构表达层，将当前绑定在 Structure Group 内的语义拓扑、布局方法和视觉样式适度解耦。

## 二、当前架构诊断

### 2.1 已经成立的基础

当前系统有三个不应推倒的基础：

1. HTML 已经是布局的单一来源，经过 `ResolvedVisualTree` 编译为原生可编辑 PPTX，而不是维护 HTML 与 Native Builder 两套坐标逻辑。
2. 正式生成通过资产清单、核心状态和 `runtime.renderer` 控制，未经审核的候选资产不能进入正式流程。
3. 已经存在一次受控的语义细化反馈：视觉导演发现内容结构不足时，可以要求内容导演从原稿中补充明确存在的分点。

### 2.2 当前资产状态

截至本次调研，仓库内共有 90 个资产清单，其中：

- 16 个核心 HTML 结构图；
- 70 个待审核 HTML 结构图；
- 4 个核心 Skin 资产；
- 已建设的结构图主要覆盖 14 类 Logic；
- `catalog/logic-map.json` 定义了 20 类 Logic，其中 `goal-alignment`、`role-stage`、`containment`、`network`、`journey` 和 `spatial` 尚无正式核心资产。

这表明当前扩容已经很快，但扩容单位仍然主要是“一个完整结构图”。如果继续沿用这一颗粒度，Logic、拓扑、数量、密度、文字长度、媒体条件、样式和 Skin 会形成组合爆炸。

### 2.3 主要瓶颈

1. 内容结构仍偏向扁平的 `items[]`，复杂的多层、汇合、共享节点和交叉关系容易被压成一层。
2. 视觉导演当前选择的是完整 `candidateId`，没有真正选择“拓扑结构 + 布局方法 + 样式”。
3. 数量、拓扑、字段契约和视觉造型大多绑定在同一个 Structure Group 内。
4. 嵌套结构目前明确限制为一层，难以稳定表达“图中还有结构”。
5. 结构组的适配能力主要通过数量范围描述，缺少对层级深度、分支、汇合、共享节点、环路和边类型的统一声明。

因此，当前问题并不是简单的“资产数量不够”，而是资产的复用粒度仍然偏大。

## 三、建议的目标架构

```text
稿件
  ↓
内容导演：VisualStructureIR（语义关系图）
  ↓
确定性能力过滤
  ↓
视觉导演：Layout Recipe + Style Preset
  ↓
布局引擎：CSS / D3 / ELK / 固定精品模板
  ↓
HTML DOM
  ↓
ResolvedVisualTree
  ↓
原生可编辑 PPTX
  ↓
LayoutFitReport ──必要时仅反馈一次──> 内容拆分或局部细化
```

这一架构不增加新的 Agent。内容导演仍然负责叙事、拆页和结构化内容；视觉导演仍然负责选择合适的结构和视觉方案；程序负责能力过滤、布局求解、编译和失败报告。

### 3.1 增加 VisualStructureIR

内容导演不应只输出一串同级项目，而应输出紧凑的语义关系图：

```json
{
  "nodes": [
    {"id": "a", "role": "cause", "content": "..."},
    {"id": "b", "role": "mechanism", "content": "..."},
    {"id": "c", "role": "outcome", "content": "..."}
  ],
  "edges": [
    {"from": "a", "to": "b", "relation": "causes"},
    {"from": "b", "to": "c", "relation": "leads_to"}
  ],
  "groups": [],
  "traits": {
    "ordered": true,
    "cyclic": false,
    "depth": 3,
    "hasSharedNode": false
  }
}
```

AI 只负责说明有哪些语义节点、节点是什么角色、节点之间是什么关系，以及是否存在层级、汇合、反馈和分组。坐标仍然全部由确定性程序计算。

### 3.2 将 Structure Group 解耦为三个部分

| 层级 | 负责内容 | 示例 |
| --- | --- | --- |
| Layout Recipe | 结构怎样排列 | 水平流程、分层树、环形、泳道、DAG、矩阵 |
| Style Preset | 结构长什么样 | 徽章、玻璃卡片、柏林蓝、线框、立体环 |
| Content Slot | 结构内部允许放什么 | 标题、正文、分点、图标、嵌套子结构 |

例如，“六项循环”不应是一份单独维护的代码，而应是：

```text
LayoutRecipe = radial-cycle
itemCount = 6
StylePreset = overlapping-arrow-ring
```

数量和内容变化由布局系统吸收，视觉精髓仍由经过审核的 Style Preset 保持。

这与 Figma 的组件思想相近：Auto Layout 负责内容增删后的自适应重排，Variant 表示真正不同的状态，Slot 负责灵活内容，而不是为每种数量和内容组合复制一个组件。

### 3.3 建立小型布局引擎组合

不建议建设一个试图解决所有问题的万能布局算法。更合理的是在统一接口下使用少量专门引擎：

- CSS Flex/Grid：并列、长文卡片、简单流程、表格和矩阵；
- D3 Hierarchy：组织树、分层树、径向树和圆形分区；
- ELK：复杂流程、DAG、交叉连接、端口、复合节点和分层图；
- 固定精品模板：循环箭头、天平、冰山、漏斗等具有强设计特征的结构。

统一接口可以保持为：

```text
measure → layout → render → fitReport
```

布局引擎只求解位置和连线，最终视觉仍由 HTML 组件渲染，HTML 仍然是编译前的唯一布局来源。

### 3.4 用能力声明代替数量穷举

Structure Group 除了声明 `itemCount`，还应逐步声明拓扑能力：

```json
{
  "topology": {
    "cyclic": false,
    "maxDepth": 3,
    "allowsBranching": true,
    "allowsMerge": true,
    "allowsSharedNode": false,
    "edgeDirections": ["forward"]
  },
  "capacity": {
    "maxNodes": 12,
    "maxTextPerNode": 60
  }
}
```

正式选择过程应为：

1. 程序先剔除拓扑不兼容、容量不足、缺少必要媒体或无法原生编译的资产；
2. 视觉导演只在合法候选中比较审美、全稿节奏、内容密度和样式重复；
3. 无合法候选时返回明确的结构缺口，不让模型强行套用相似但错误的结构。

适用性由能力匹配产生，而不是由模型猜测哪个模板看起来接近。

## 四、无法穷举时的受控降级

适用性不等于把任何内容都强塞进结构图。建议固定四级出口：

1. 有完全适配的精品 Structure Group：优先使用；
2. 没有精品图，但关系可以由通用布局表达：使用品牌化的通用树、网格、流程或 DAG；
3. 内容过于复杂但可以拆分：返回内容导演拆成两页，只允许一次反馈；
4. 关系本身无法稳定结构化：退化到设计良好的正文排版，而不是临时创造结构图。

现有一次语义细化回路可以扩展为少量标准请求：

- `split-node`
- `extract-children`
- `merge-nodes`
- `split-page`
- `choose-editorial-fallback`

反馈必须保持紧凑、结构化，并限制为一次；不增加自由循环和新的 Agent，避免工作流再次变重。

## 五、结构图美化的系统化方向

通用布局算法只能保证结构可读和不发生碰撞，不能自动保证审美质量。美感仍需通过入库线积累，并拆解为可复用的视觉语法：

- 字体角色：标题、节点标题、正文、注释、数字；
- 空间节奏：外边距、组间距、卡片内边距、留白比例；
- 形状语法：圆角卡片、徽章、色块、环、立体折带；
- 连接语法：直线、折线、弧线、箭头叠压、虚实和粗细层级；
- 强调语法：主节点、关键路径、结论、风险和反差；
- Skin Token：颜色、字体、Logo 和页脚，不参与结构拓扑。

来源 PPT 蒸馏时，应分别提取：

1. 语义骨架：它表达的关系和信息角色；
2. 布局配方：节点、分组和连线如何组织；
3. 视觉配方：字体、色彩、形状、连接和强调规律。

HTML 审核阶段可以继续优化审美，但批准后的改进必须被固化为 PPagenT 自己的 Token、Recipe、Primitive 或 Style Preset。正式生成线不得临时调用外部设计 Skill。

## 六、参考项目与可借鉴方案

### 6.1 优先借鉴

| 项目 | 对 PPagenT 的价值 | 建议 |
| --- | --- | --- |
| [Figma Auto Layout](https://help.figma.com/hc/en-us/articles/360040451373-Explore-auto-layout-properties) 与 [Slots/Variants](https://help.figma.com/hc/en-us/articles/38741465279895-The-difference-between-slots-instance-swaps-and-variants) | 内容槽、嵌套、自适应和真正的状态变体 | 直接借鉴组件模型 |
| [Penrose](https://github.com/penrose/penrose) 与 [Penrose 论文](https://www.cs.cmu.edu/~kmcrane/Projects/Penrose/Penrose_OBT.pdf) | 将语义对象和视觉样式分离 | 直接借鉴 IR 架构 |
| [Eclipse Layout Kernel](https://eclipse.dev/elk/) | DAG、端口、复合节点和复杂连线 | 作为复杂拓扑布局后端 |
| [D3 Hierarchy](https://d3js.org/d3-hierarchy) | 树、径向和分区布局 | 作为层级布局后端 |
| [Storybook Visual Tests](https://storybook.js.org/docs/writing-tests/visual-testing) | 将组件状态形成可审核样例和视觉基线 | 借鉴其 State Lab 思路，优先升级现有 PPA 看板 |
| [Beautiful.ai Smart Slides](https://www.beautiful.ai/smart-slides) | 内容变化后自动调整间距、文本和视觉，主题与布局分离 | 借鉴产品行为，不依赖其内部实现 |
| [W3C Design Tokens](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/) | 统一颜色、字体、间距和形状参数 | 用于 Skin 与 Style Preset 解耦 |

Beautiful.ai 值得借鉴的关键不是模板数量，而是每个 Smart Slide 都知道自己能容纳什么、内容变化后怎样调整，并可为同一内容提供多个合法布局。[Slide AI](https://support.beautiful.ai/hc/en-us/articles/43350069148557-Create-and-Edit-your-Slides-with-Slide-AI) 体现了这种局部替换和比较思路。

### 6.2 特定场景参考

- [Cytoscape.js](https://js.cytoscape.org/) 或 [AntV G6](https://g6.antv.antgroup.com/en/api/layout)：适合生态网络和主体关系网，不建议用于普通并列或流程页；
- [React Flow](https://reactflow.dev/examples)：适合以后在 PPA 看板中增加人工拓扑编辑，不应成为正式渲染核心；
- [PPTist](https://github.com/kuochiakun/PPTist)：可参考浏览器端 PPT 元素编辑交互；
- [PPTAgent](https://github.com/icip-cas/PPTAgent)：可借鉴参考页功能分类、内容 Schema 和结果评估，不建议把自由迭代编辑引入正式生成线；
- [Presenton](https://github.com/presenton/presenton)：可参考 PPT 模板导入、HTML 模板制作和本地生成体验；
- [dom-to-pptx](https://github.com/atharva9167j/dom-to-pptx)：适合与当前编译器建立功能对照测试，不建议直接替换已受控的 PPagenT 编译器；
- [PptxGenJS](https://github.com/gitbrent/pptxgenjs)：可作为原生 OOXML 后端参考，但其 HTML 支持主要面向表格，不是任意 HTML 组件转换。

### 6.3 可用于入库线的 Skill

- [Anthropic frontend-design](https://github.com/anthropics/skills)：适合来源资产进入 HTML 后的第一轮视觉设计；
- [Impeccable](https://github.com/pbakaus/impeccable)：包含 critique、polish、layout、typeset、distill 等操作，适合复现后美化和提炼视觉规律；
- [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)：适合审查 PPA 看板与 HTML 组件的可读性、响应性和界面问题；
- [Canva Skills](https://github.com/canva-sdks/canva-skills)：可选作品牌检查和外部设计反馈，但不应成为正式生成依赖。

外部 Skill 必须限定在蒸馏、实验和审核环节。其输出经过人工确认后，应蒸馏为本项目可版本化、可测试的规则，避免正式运行结果随外部 Skill 更新而漂移。

### 6.4 不建议作为正式后端

Slidev、Marp 等 Markdown 演示方案可以借鉴主题和内容组织方式，但不适合作为 PPagenT 正式后端：

- [Slidev](https://sli.dev/guide/exporting.html) 的 PPTX 导出主要是图片页；
- [Marp](https://github.com/marp-team/marp) 的可编辑 PPTX 仍属于实验能力。

它们不能稳定满足 PPagenT 对原生可编辑和结构可靠性的要求。

## 七、建议的最小实施路线

当前不宜立即重写编译器，也不宜一次性迁移全部待审核资产。建议先进行一个小型架构实验。

### 7.1 选择三个代表 Logic

- `sequence`：验证简单线性结构；
- `hierarchy`：验证多层和不均衡树结构；
- `causal`：验证分支、汇合、共享节点和复杂连线。

### 7.2 建立最小能力

1. 定义 `VisualStructureIR v0.1`；
2. 定义统一布局接口 `measure → layout → render → fitReport`；
3. 接入 CSS Grid/Flex、D3 Hierarchy 和 ELK Layered 三类后端；
4. 允许现有精品结构以 `fixed-template` Recipe 继续运行；
5. 不改变 HTML → `ResolvedVisualTree` → 原生 PPTX 编译链；
6. 将 Style Token 与拓扑布局逐步分离，而不是一次性重写全部资产。

### 7.3 在 PPA 看板中验证边界状态

看板应自动展示：

- 最少、常用和最多节点；
- 长文本与短文本；
- 一层与两层结构；
- 分支、汇合和共享节点；
- 有无图标和图片；
- HTML 与原生 PPT 预览；
- 溢出、重叠、字号下限和连接线交叉等 FitReport。

不需要穷举所有笛卡尔组合，优先覆盖最小值、默认值、最大值和高风险边界状态。

## 八、最终判断

PPagenT 的适用性不能靠无限增加完整模板获得，也不应靠 AI 自由绘图获得。更稳妥的方向是：

> 用有限的语义类型、有限的布局算子和有限的视觉配方，组合出大量受约束、可审核、可编辑的结构实例。

因此，下一阶段最值得验证的不是“还能再做多少结构图”，而是现有结构图能否被拆解成：

```text
语义图 + 布局配方 + 样式配方 + 内容槽
```

如果三个代表 Logic 的最小实验能够证明同一份语义图可以稳定切换不同布局和样式，并保持 HTML 与原生 PPT 一致，再逐步迁移其他 Logic；如果无法证明，则继续保留当前固定精品模板与简单正文降级，不进行大规模架构迁移。
