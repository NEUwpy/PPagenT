## 一、Jev 是什么

TypeSafe AI（创始人 Diogo Almeida，前 OpenAI，参与 RLHF/InstructGPT）2026-09 发布的**通用决策模型**，官方称 System One Model（卡尼曼快/慢思考的系统 1）：

- **只做结构化判断，不生成文本**：输入 state，输出 Choice / Score / Yes-No + **校准过的概率与置信度**。官方定位"unstructured state in, typed probabilistic decisions out"——给软件当"智能判断函数"；
- **速度/成本**：平均单判断 ~380ms，比常规 LLM 快 20–200 倍、便宜 40–400 倍（$0.042/M token，输出 token 免费——因为只输出一个决策）；可一秒决策 10 次、可一次并行问多个问题；
- **训练方法 RLCD**（Reinforcement Learning for Calibrated Decisions）：优化的不是"回答好不好"，而是**决定对不对 + 说的置信度是否真接近该置信度**——校准是核心卖点，使"概率"可以直接接控制流（如 >0.90 自动执行 / 0.7–0.9 交强模型复核 / <0.7 交人）；
- **并行判断**：一条输入可同时挂十几个问题一次返回；
- **名字来源**：杰文斯悖论——判断效率提高→总判断量暴涨；赌"智能的消耗大头其实是最小判断"；
- 已接入 Vercel AI Gateway 可试用。

**证据成色提醒**：卡兹克文的对比数据（vs GLM/DeepSeek/Qwen Flash 预筛与聚簇任务）是第三方单点测试且带宣传性质；官方 evals 也是厂商自测。**任何结论都要在我们自己的语料上 A/B**。

## 二、与 PPagenT 的契合度分析

### 现状对齐：我们的 harness 已经在走"分派"路线

| 判断类型 | 现状归属 | Jev 候选度 |
| --- | --- | --- |
| 确定性（越界/重叠/面积/字数/几何/覆盖/模板映射） | 程序 checker + 求解器 | **不用 Jev**（代码更快更准） |
| 模糊小判断（密度失衡、块值不值得独立成区、是否需要重规划、失败要不要触发修订） | 目前由主 Agent 一并承担（既当导演又当裁判） | **高**——这正是 Jev 的形状 |
| 创造性（理解/提炼/重组/文案/页面主题） | 主 Agent | **不用**（Jev 不能生成） |
| 视觉（看截图） | VLM 诊断（开发侧） | **不用**（Jev 不吃图像） |

关键优势：**我们不需要让 Jev 看图**——渲染前本就有机器可读 PagePlan/gray-plan（区块面积、字数、role、kind），喂结构化 state 即可判断密度失衡/主次合理性。

### 三分法分工（接入后的理想形态）

```
代码：确定性规则（已有：几何/覆盖/模板映射/checker）
Jev：模糊小判断（校准概率，代码按阈值分流：自动执行/复核/问人）
Agent：开放性创造（理解/提炼/重组/生成）
VLM：只在真需要"看页面"时审图（开发侧）
```

### 立即可对口的四个高频决策（最小实验设计）

1. `presentation_mode`：基础排版 / 结构 Skill / 图表 / 表格（Choice）；
2. `basic_skeleton`：单主体/主次双栏/对等双栏/上下承接/多卡片/网格/头带主线（Choice）——**注意**：这与刚拍板的模板化第 7 条重叠；模板映射表已用确定性规则做了一遍。Jev 的位置应是**映射表的"映射不出"兜底**（现有保守默认=单主体/column），以及覆盖时的合理性裁判；
3. `density_balance`：过疏→过密五级 Score——**可直接替换手工调的 55%~75% 空洞阈值**（该阈值边界正是已记账盲区）；
4. `needs_replan`：审稿打回后"修这一版还是重规划"——现在的死循环风险点（历史上 214s/24 轮失败跑即此病）。

### 我们已具备的实验资产（别人没有的）

约 30+ 个 run 目录沉淀了带人工判定的**明显好/明显差页面**（Boss 线八轮评审 + 泛化考试归因列）——即免费的高质量标注语料。Jev 一到货即可离线回放测试：给 PagePlan 特征，比对它是否复现人工判定。**通过后才讨论接入生成线**（纪律 3：改变运行时倍率的机制须附成本数据）。

### 边界与风险

- Jev **不看图像**（官方材料：state 为结构化/文本）——视觉判断仍归 VLM；
- 不能创造：提炼、改写、新结构不受影响；
- **中文领域文本的校准未验证**：官方/第三方样本多为英文通用任务，PPT 归属/密度判断是中文长文场景，须先测；
- 外部服务依赖：访问资格/国内延迟/价格稳定性；接入须走 provider 抽象层（现有 `chat-provider.mjs` 模式）；
- **判断碎片化风险**：整页规划是全局权衡，拆成微判断可能丢失整体叙事一致性（见下）。

## 三、对"可靠性=填表单"想法的评估（用户 2026-09-18）

用户的直觉：可靠生成 PPT 可以通过"填表单"实现。评估：

**我们已经有一半是表单**：gray-plan-3 就是表单 schema，check_plan 就是表单校验，每轮正文重写完整计划就是"重新填一遍表"。协议失败（忘带计划/坏 JSON）说明"一次填一张大表"对模型仍有负担。

**Jev 路线是把大表拆成微决策**：每页若干个校准过的小判断，代码按概率控制流——这正是 TypeSafe workflow evals 的做法（把 policy 拆成小 Noul/Choice/Score，代码控制流程，官方报告比单 prompt 更准/更快/更便宜，但系厂商评测）。

**利弊**：
- 得：判断稳定可校准、成本低、失败模式从"整张表报废"变成"单字段回退"；
- 失：微判断失去全局一致性——页面是整体构图，逐字段填表可能"每格都对、整页不搭"（类比：审稿契约强调 narrative 的全局性）。

**建议形态：混合**——保留 plan JSON 作为创造性产物（一次成表），Jev 作为**裁判层**只接管具名的模糊决策（上列四个），并给校准阈值：高置信自动执行、中置信交主 Agent 复核、低置信升级 semantic_review 或人工。这样主 Agent 从"导演+裁判+质检"三职中解放裁判职，与现 harness 的分派方向一致。

## 四、行动建议

1. **等 access 到手后先做离线回放实验**（不动生成线）：用已归档 runs 的 PagePlan+人工判定作测试集，验证 4 个具名判断的准确率与校准质量（重点：中文、PPT 领域、中文长文本密度判断）；
2. 通过标准：四判断在标注集上与人工判定一致率 ≥85%，且校准曲线可信（说的置信度≈实际频率）；
3. 通过后按纪律 3（成本增量数据先行）接入 `needs_replan` 与密度 Score 两处试点——它们是当前最能止血的两处；
4. 不接：文案生成、视觉判断、结构创造。
