# PPagenT 产品需求

版本：v0.2，2026-09-05。状态：**核心改动权限、可用标准及交付／修改方式已确认；其他建议与待确认项分别标注**。

本文描述用户提供什么、希望得到什么，以及怎样判断结果可用。不规定模型、Agent 数量、Harness、Skills、结构库或生成技术，也不表示这些需求已经实现。已有架构设想见[产品定义](产品定义.md)，不能用某一种现有实现倒推或收窄这里的用户需求。

## 1. 核心需求

用户提供不同成熟度的内容，以及必要的演示要求，系统完成所需的内容整理和视觉编排，在合理等待后交付内容可靠、表达清楚、视觉合适、可以继续修改的演示文稿。

核心价值是减少用户从内容到可用演示之间的反复判断与调整，不要求用户先学会拆页、选择结构或设计版式。

主要成品为原生可编辑 `.pptx`。是否还单独交付文字讲稿，见末尾待确认项。

## 2. 四类输入需求

以下四类来自本轮用户描述，按内容状态区分，不按扩展名区分。同一个 Word 或 PDF，既可能是讲稿，也可能是待讲解的材料。

| 类型 | 用户已有的内容 | 希望系统完成的工作 | 内容改动边界 |
| --- | --- | --- | --- |
| A. 讲稿转演示 | 自己写好的演讲稿、讲课稿、汇报稿，不限定概念上的文件载体 | 理解已有叙事，提炼、分章、拆页并完成视觉编排 | 允许改写文字、调整顺序和重新组织，前提是不改变原意 |
| B. 材料转演示 | 要讲解的论文、报告、PDF、Word 等资料，尚未形成讲稿 | 理解材料，根据演示目的选择重点、建立讲述顺序，再制作 PPT | 可以整理和取舍，不能把材料没有的结论写成材料事实 |
| C. 已有 PPT 优化 | 已有演示文稿，希望润色提升 | 在现有内容基础上改善文字、版式和整体风格 | 默认允许文字润色和顺序调整，不限于美化；必须保持原意，遵守用户明确要求保留的内容 |
| D. 简短需求转演示 | 一句话、一个主题或一段简短需求 | 先形成可审阅的内容稿或大纲，再据此生成 PPT | 不能假装已经获得用户未提供的个人经历、组织事实或业务数据 |

“不限定文件载体”是目标需求，不等于首版承诺读取任意格式。首批支持格式、扫描件／图片文字识别、文件大小及多文件组合范围需另行确认。无法可靠读取时，应说明具体缺失，不静默忽略。

## 3. 建议补充的共同任务条件

这些条件用于帮助系统理解演示任务，不要求用户每次填完一张复杂表单：

- **讲给谁、为了什么**：受众、场合及希望传达的重点。
- **讲多长、做多少**：目标时长或页数；两者冲突时说明取舍，不通过持续缩小字号硬塞。
- **希望怎样呈现**：组织视觉规范、已有风格或视觉参考；没有要求时应有可用的默认方案，默认选择规则待确认。
- **哪些内容必须保留、允许改到什么程度**：尤其适用于用户自己的讲稿与已有 PPT。

信息足够时直接推进；只有缺失信息会显著影响内容正确性、任务方向或改动范围时才追问。非关键假设应可见、可修改。

## 4. 用户侧流程与两种使用方式（已确认）

1. 提供讲稿、材料、已有 PPT 或简短需求，并补充已有的演示要求。
2. 系统识别需要做的工作及缺失信息，按输入状态完成必要的内容整理。
3. 默认直接完成内容整理、页面编排、生成与检查，交付 PPTX 和便于浏览的预览。
4. 用户可以直接使用或手工编辑成品；不满意时，在该成品基础上继续多轮对话，修改特定页面。

两种使用方式是：

- **直接交付：默认、主打方式。** 输入足够时，用户无需逐步确认大纲、逐页内容或版式，系统直接交付经过检查的完整成品。
- **对话修改：基于已有成品继续迭代。** 用户可以多轮提出修改意见，指定某页或若干页；系统以当前版本为基础修改，而不是默认重新制作整套。

这里描述用户行为，不要求产品一定设置两个独立入口或模式开关。直接交付后可进入对话修改。

这是一条用户可理解的工作过程，不规定内部实现。A、C 类不应为了统一流程而强迫用户先重写整份讲稿；B 类不一定必须产生完整逐字讲稿；D 类需要先形成内容，但默认不把人工确认内容稿设为制作 PPT 的必经门槛。缺少会影响事实或任务方向的关键信息时，仍须澄清，不能以直接交付为由自行编造。

后续修改是核心体验：用户可以要求某页更简洁、改写文字或调整讲述顺序。允许改文字、调顺序，但必须保持原意；明确限定为局部修改时，不应无故改变其余已认可内容。用户在 PowerPoint 中手工编辑文件与通过对话让系统修改，均需支持。

## 5. 交付物与可用标准

### 5.1 交付物

- **主要交付**：可继续编辑的 PPTX。
- **查看方式**：能方便浏览整套演示及逐页内容，不限定预览采用何种技术。
- **中间内容**：整理后的大纲、页面内容稿或演讲稿是否单独交付、按需提供还是默认提供，待确认。

### 5.2 验收底线（已确认）

| 维度 | 用户能观察到的结果 |
| --- | --- |
| 内容可靠 | 不编造事实、数据和来源；重要论点、限定条件与图表含义不失真；材料事实、用户观点与新增建议有区别 |
| 表达清楚 | 有合理的讲述顺序，拆页和信息层级服务受众与时长；不是简单把长文逐段搬上页面 |
| 视觉合适 | 风格统一、标题正文层级清楚、内容重心合理；没有明显溢出、碰撞、穿字、失真或难读的小字 |
| 适应内容 | 能处理纯文字、图文、对比、流程及多区域组合；不要求每页画结构图，也不把全稿强套一种页面结构 |
| 可继续编辑 | 标题、正文和系统生成的关系图等可作为独立对象修改；不能用整页截图冒充可编辑成品 |
| 忠实保留素材 | 照片、截图、论文原图可保留为图片对象，保持比例与必要图注；不承诺将任意来源图片自动还原为可编辑数据图表 |
| 可修订 | 用户能手工修改最终文件，也能在成品基础上多轮对话修改特定页；允许改写与重排但不改变原意，局部修改不无故改变其他已认可页面 |
| 交付透明 | 有可理解的任务状态；无法读取、缺少依据或尚未解决的问题明确告知，不把部分完成当成完整交付 |

“经过一段时间”需要后续转为可验证的时效目标，但现在不虚设分钟数、成本上限或成功率。至少应避免无期限等待，也不能为了宣称成功而牺牲内容真实性与可编辑性。

## 6. 当前不作承诺的事项

- 四类输入是否首版同时提供，以及各自优先级。
- 任意文件格式、任意篇幅或任意复杂度都能可靠处理。
- 一次生成必然达到最终审美，无需用户反馈。
- 根据一句话就能推断所有背景、填补真实业务数据，或自动完成有充分依据的专题研究。
- 所有来源图片都重建为原生图表、公式或可编辑插图。
- 某种特定实现架构是满足需求的唯一方式。

原始用户文件的保留、上传处理、外部资料检索、历史版本及数据保存策略，需要单独确认后形成相应要求，不在本稿中默认授权或指定实现。

## 7. 待确认的问题

1. **附加文字稿**：除 PPTX 外是否还要独立文字稿，具体是大纲、逐页内容稿还是完整演讲稿？
2. **首版范围**：先覆盖哪类输入、哪些格式？图文与多文件混合的支持范围是什么？
3. **可接受的服务条件**：目标等待时间、成本，以及具体客户端兼容范围如何确定？

这些问题不妨碍先明确“四类输入，最终得到可用且可修改的演示”这一共同目标；但会影响后续的交互、范围和验收，不应由技术架构替用户作决定。
