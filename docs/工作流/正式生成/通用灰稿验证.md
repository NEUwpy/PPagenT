# 通用内容规划与灰稿验证

本入口验证永久内容规划环节：完整原稿 → 信息提炼与页面职责 → 表达选择与文案重组 → 内容检查 → 基础排版选择 → 实文测量与区域求解 → 原生灰稿 → 实际审阅及反馈修订。M1 检验页面级信息架构，目标是得到无需人工重新组织的可读灰稿；当前只交灰稿候选，不接正式美化，也不表示 M1 或跨稿稳定性通过。

2026-09-16 用户指定的过程范本见 [原稿到页面：不足与感悟](../../PPT制作规则参考/内容提取/原稿到页面-不足与感悟-20260916/笔记.md)。学习顺序为：原稿提炼 → 按归属分支 → 各分支的条目要点与实文说明 → 按局部关系选择表达 → 实文容量与空间调整。先形成实文提纲，不代表先冻结坐标；选择表达后仍可修订文案与容量。范本中的两个类别、各 2／4 项是示例，不能写成页型或固定模板，也不能把两个类别误称为有证明关系的两个观点。

与代码对应：`groups` 承载本页的分支职责，`blocks` 承载分支内条目，`label / text` 区分要点与展开。原先只有组级 `kind`，使某条目需要图示时容易整组蓝化或被拆成无归属的独立区域。本次在文字组的 block 上复用可选 `kind / expression / relationship / production`，不设新角色或任意深度树；block 缺省为文字，局部非文字块显示原有四项浅蓝制作说明。实际显示投影、审稿输入、容量测量和原生渲染共用这些内容，包含局部蓝区内边距。此承载能力的验证不代表模型已能自动稳定完成信息组织；也未迁移到 Harness 镜像包。

2026-09-16 接续修订：完整不是逐字搬运。原稿保留为事实依据，规划可以提炼、合并重复信息、长句改短语，并按表达需要重组实文；重要事实、条件、否定及关系必须保留。已有 role、claim、kind 继续使用，不另建页型枚举或自报密度等级。表达选择使用 `content-stages.mjs` 的组引用绑定：原内容组恰好引用一次，可以共同进入一个表达，重写文案只可引用被绑定组的来源；随后仍进行来源保真及实际可见内容审稿。进入几何阶段后才冻结内容。旧逐字分组试点 `prepareContentDraft/bindExpressions` 的契约保持原样。

审稿输入由与测量、渲染相同的 `grayDisplayBlocks` 派生，明确区分灰色实文、浅蓝制作说明及后台职责。后台叙述不能充当上屏证据。模型审稿仍可能误判，尤其不能用 accepted 代替视觉验收。主题句按28px单行测量。灰稿同排主体栏共用上下边界；栏内按已有 blocks 划分子区，文字区为灰色，制作说明为浅蓝色，不绘制蓝区内部节点。块内按实文测量最小高度与内边距，剩余高度按各块所需高度分配，固定块间距。不能仅拉长外框、把文字全部堆在上方，也不能按条目数量机械决定两栏比例。这是空间组织约束，不代表已经完成视觉验收或自动权重判断。

运行目录与实验名称不属于稿件内容。`area.label` 只用于状态及预览标识，规划、表达、审稿与排版输入只接收区域宽高，避免将“范本页”“原退回案例迁移”等后台标签写入上屏标题。预览也不统一添加“模拟内容”；原稿含模拟性质时仍由实际主题或正文明确承载。

2026-09-16 局部试验从 `gray-draft-2` 简化到 `gray-draft-3`。内容计划使用 `gray-plan-3`：保留目的、主题句、组职责、实际文案与必要关系的一句话说明，不再要求逐句关系边；组与条目的数组顺序就是阅读顺序，条目标签可省略。每组必须选择 kind，但普通文字不要求调用结构库。

排版调用只返回每页的 `single/row/column/grid`、可选横向宽度权重或网格列数，禁止返回坐标、正文或新分组。`src/runner/gray-layout.mjs` 使用同一文字测量逻辑计算容量，再调用现有 `src/composition/resolve.mjs` 的 `resolveLayoutTree` 求区域；无需为了使用几何工具补造逻辑关系。正文区分配与文字最小容量分开，栏内子区同样复用该求解器；不新增语义分类或几何引擎。几何失败先在同一内容计划下尝试其他组合（最多三次排版调用），仍失败才返回规划。旧版候选仍可重放，续跑会采用新规划契约。

四类规则为内容结构、Skin、通用排版、风格。该入口实际加载根目录 `rules/内容结构.md`、`rules/页面组合.md`、`rules/排版.md`；没有将语义契约自动迁移到其他正式导演入口或 Harness 镜像包。

在仓库根目录运行，继续使用既有 `config/deepseek.local.json` 或 Provider 环境配置、运行器状态与 PPT 引擎：

```powershell
node src/runner/gray-draft.mjs --source 原稿.md --output 新运行目录 --width 1170 --height 492 --label 内容区域 --max-revisions 4
node src/runner/gray-draft.mjs --source 原稿.md --output 原运行目录 --width 1170 --height 492 --label 内容区域 --resume --feedback 审阅反馈.md --max-revisions 4
node src/runner/gray-draft.mjs --replay 原运行目录/state.json --output 新重编译目录
```

同一流程也可从生产工作台（`启动PPA生产工作台.cmd`）运行：上传稿件、给定宽高与标签后停在等待审阅；每一步的提示词、规则快照、模型响应与程序检查按轮在步骤阅读器里查看，「对比运行」可并排两条运行逐步对照。工作台不改变本入口的检查与记账方式，产物目录结构一致；工作台发起的运行会在工作台内续跑（等价 `--resume`），人工反馈注入仍走 `--feedback` 文件。

反复修订未收敛时，可在 `--resume` 时加 `--fresh-plan`，保留旧版本但不把旧逐页规划送回模型，重新依据原稿、区域及反馈规划。

首次输出目录必须不存在（工作台运行的输出目录由其预先建立并含 `input/`，调用时显式传入 `existingOutput`；CLI 默认行为不变）；恢复核对原稿哈希与区域尺寸。`--max-revisions` 是本次首轮后的额外修订次数。恢复保留 `revision-N` 与人工反馈；已有 PPT 存在时，新版本放在对应 revision 的 artifacts 下，当前指针见 `state.json` 的 `grayDraft.artifactDirectory`，不能只看目录根部的旧 PPT。

尺寸为真实内容区设计像素，支持宽高 240–4000；主题句在内容区外，画布宽高分别增加80与150。正文22–28px、区域标题26px、主题28px。灰区呈现实文，浅蓝区呈现表达作用、承载内容、基本关系、制作要求。四种验证尺寸无单独分支，页数由模型决定；当前单次规划保护上限100页，超出明确失败，不静默裁页。

`state.json` 是机器真源；`plan.json`、`content.md`、`state.md` 是派生视图。PPT 与预览均从其中页面内容和 regions 构建。`revision-N` 保存模型响应、usage、程序检查、语义审稿及修订；`human-feedback-N.md` 保存外部审阅依据。新调用保存系统提示快照，早期试验的提示变化在本轮报告说明。

程序检查覆盖来源引用、块级数字与引文、表达方式、排版绑定、区域边界/重叠、固定字号容量及原生文本完整性。v3 不强制关系图，若提供关系仍检查端点；旧版继续检查原关系契约。语义检查对照完整原稿，检查事实、条件、逻辑、页面职责及内部信息组织；组织实质失败须返工。原稿的模拟声明必须实际显示，仅引用来源不算显示；内部规划和审查解释不能写进正文。审稿调用未看图片，也可能漏检。导出的 PPTX 会重新导入渲染，`editable-check.json` 核对原生文字，`preview.html` 提供逐页浏览。实际视觉仍须逐页审阅，任何自动通过都不能代替用户验收。

每次 revision 留存 `content-plan.json`（提炼草稿）、`expression-response.json`（组引用、媒介与文案重组）、`semantic-plan.json`（绑定后的计划）、`visible-plan.json`（实际可见内容）、`structure-check.json`、`semantic-check.json`、`layout-response-N.json`、`layout-check-N.json` 和对应提示快照。v3 的 `layout-resolved-N.json` 中 resolved 是分配单元，occupiedRegions 是实际绘制的区域，contentMinimums 是包含文字和留白的最小容量；`plan.json` 是内容与几何绑定后的派生产物。成功状态中的 `pages` 用于渲染，`grayDraft.semanticPlan` 保存本次模型内容计划供追溯，不另行维护一份正文。模型及 thinking 配置记录在 grayDraft.providerSettings。

局部试验输入与范围说明在 `experiments/gray-information-architecture-20260916/`。这份片段不能替代旧四页原稿的四组完整验证。

基础排版简化试验记录在 `experiments/gray-basic-layout-20260916/`；同一片段验证 1170×492 与 780×328 两种内容区，使用共同代码，无专门页数或逐页布局答案。

Git 存档见 [灰稿工作存档](../../../experiments/gray-checkpoint-20260916/README.md)，包含被忽略的 outputs 运行快照、逐文件哈希及最新待审 PPTX 副本。最新主 Agent 分区修订与前版语义计划一致，用于隔离验证排版改动；外部模型失败/中断及用户退回均保留，不计作自动规划通过。

使用同一模型端点的独立审稿调用不是独立外部审查团队。当前不自动分析图像或调用结构库；蓝区表达要求就是灰稿交付内容，不能将其算作已完成图示制作。程序通过但实际灰稿失败时，通过 `--feedback` 交回模型修订，不手写逐页方案冒充模型通用能力。

## 2026-09-17 内容规划普适问题修正（附着性内容与主体文字承载）

模拟稿「值班交接安排」（晚间交接 → 次日早班；交接单丢失时向主管报告、不得凭记忆补记）暴露两个普适问题，均按通用原则在契约与规则层修正，不针对该稿写补丁。

**问题一：附着性内容与主体内容同层并列。** 首轮规划把「交接单丢失处置」（条件触发的异常处置）与两个流程环节铺成三个并列组，claim 也把异常处置算成流程的第三项要求。修正：条件触发的处置、异常、例外与禁令属于附着性内容，注明依附对象、从属并紧邻所依附内容，不与主流程环节或并列要点铺成同层组；判断依据是依附关系而不是篇幅。落点：`rules/内容结构.md`、语义规划契约、表达选择契约。

**问题二：主体职责整组改选非文字表达后正文不上屏。** 带人工反馈修订时模型把主流程整组改成 flow，灰稿中该组只呈现蓝区制作说明、灰区没有正文，语义审稿连续两轮拒绝（"主流程没有可读的实际文案"）。修正：承担页面主体叙述（主流程环节、并列要点、分类依据等）的组保持 text，时序与结构写在实文和蓝区说明里；审稿明确检查"主体内容只在制作说明中复述不算落实"。落点：语义规划契约、表达选择契约、语义审稿契约。

同时吸收外部学习资料《内容的提取》（小红书十一图，见 [内容提取笔记](../../PPT制作规则参考/内容提取/小红书-670890aa000000001b020005-内容提取及可视化/内容的提取.md)）中与本次失败相关的通用方法：先用短句总结各部分说了什么、再判断关系类型（因果按先后、对比按共同维度、时间按时间线、只有并列关系才平铺）；重复出现的术语与专有名词通常承担重点，结论进入主要位置，与主体无隶属关系的细节不升级成独立区域。落点：`rules/内容结构.md`。

**修后验证**（2026-09-17，工作台灰稿线，无人工反馈的自动修订）：

- 「值班交接」重跑：附着性分类首轮到位（主流程合并为一组，丢失处置作为该流程之外的 supporting 条件组）；但主流程前三轮仍尝试整组选 flow，被语义审稿连续拒绝，第四轮改回文字表达后通过。分类问题一次到位；主体文字约束模型尚未首轮遵守，由审稿兜底，代价是三轮返工，留待继续观察是否需要在规划契约中进一步加强。
- 「文件保存方式」重跑：首轮通过，共同命名要求正确归为 supporting 组，简单稿未被新约束破坏。

以上为契约修改后的单次验证，不宣称跨稿稳定或 M1 通过；实际灰稿仍须逐页审阅与用户验收。

## 2026-09-17 多稿类型验证与模拟声明修正

用四份不同结构的模拟稿（对比型、时间型、多分支并列型、结论论证型）走工作台灰稿线，全部自动修订、无人工反馈，检验"结构是否随内容变化、不套模板"：

- **结构适配成立**：时间型=单组四时间节点；对比型=两种模式配对＋共同要求降级；多分支=三分类条目＋共同要求；论证型=现有记录＋建议。没有出现同一结构套所有稿件。
- **暴露缺陷：模拟声明处理不稳定**——首轮六份中四份出错（两份完全丢失、一份混入某条具体整改且重复、一份独立成组"说明"），语义审稿也漏检；与 9 月 16 日台账记录的"模拟性质遗漏、审稿漏检"同源。
- **修正**：契约把模拟/假设声明要求写死——原稿给出就必须上屏且恰好一次，最自然位置是页面主题句或紧邻主体的一条；不得省略、逐条重复、独立成组。审稿契约同步增加检查。
- **修后复跑四份**：全部在主题句携带声明，无重复、无独立成组；通过轮数 1–2（论证型由 3 轮降到 1 轮）。对比型首轮因"比较内容整组进蓝区"被审稿拒、次轮改文字通过——"主体保持文字"仍需审稿兜底，留在观察项。
- 另记录一处表达与布局的耦合：论证型修复前首轮把三组并为一组、布局无法分栏（weights 报错），靠自动修订拆开；暂不改机制。
- 本验证是单批四份；不宣称跨稿稳定或 M1 通过，等待用户审阅实际灰稿。

## 2026-09-17 灰稿线收成 Agent 自主闭环

把阶段链（程序固定编排：规划→表达→审稿→布局→渲染）收成为**模型自主闭环**：新增 `src/runner/gray-agent.mjs`，模型拿到原稿与三个确定性工具——`check_plan`（程序检查）、`semantic_review`（独立审稿）、`render_draft`（布局求解与原生渲染）——自己决定先做什么、何时检查、何时修订、何时渲染；渲染成功即交付，程序只提供工具与闸门。计划等大对象走消息正文，工具参数只留小控制字段（小模型在嵌套工具参数里写长 JSON 会反复写坏，这是定位到的卡点）。

- 工作台灰稿线已切换：步骤条为「系统提示词＋逐轮工具＋已交付」，轨迹阅读器展示每轮模型输出与工具结果；旧的阶段链实现（`gray-draft.mjs`）保留在仓库作为历史与对照，不再作为工作台入口。
- 检查器与布局求解的错误消息改为可定位到组/块/字段与修法（模型自纠依赖可定位反馈）；这条对阶段链同样生效。
- 验证（2026-09-17）：五份不同结构稿件（值班交接/对比/时间/多分支/论证）全部一次交付（9–15 轮，单次约 11 万 tokens、绝大部分缓存命中）；工作台端到端五轮交付。同一交接稿此前在阶段链上曾出现修订预算耗尽。
- 边界如实记录：Agent 运行的修订/续跑（人工反馈后再跑一轮）尚未建设，界面明确拒绝并说明；时间线类结构里曾把"本资料为模拟资料"放进节点条目（组内首项），声明位置偶有摆动，留待观察。

## 2026-09-17 灰稿结构草图（用户确认的 C 混合派）

用户确认的表达界限：对比（对象×共同维度）→ diagram 并置卡片；步骤、流程与时间（三个及以上节点）→ flow 顺序节点与箭头；对照网格与分类列表 → table 行式表格；纯说明且篇幅小 → 文字；数据图表与图片本轮仍是蓝区说明（写明建议表达）。灰稿为 diagram/flow/table 绘制**简化草图**（不美化、不调用结构库），框内文字就是实际文案；容量检查与原生渲染共用同一份布局测量（sketchBodyLayout），宽度不足按容量失败返回规划，不静默压缩。

实现落点：语义规划、表达选择与语义审稿三份契约（选择依据与审稿规则）；`gray-semantics.mjs` 的显示投影与 surface 描述（审稿、测量、渲染看到同一份文字）；`gray-draft.mjs` 的 sketchBodyLayout 与渲染分支（卡片/节点/箭头/表格行）。

四类稿件验证：对比=两个白框卡片并排；时间=四节点横向连线加箭头；多分支=三张对象卡片（另一次运行选了 table 三行）；论证=记录依据两卡加建议文字。结构随内容类型变化成立。

已知波动（如实记录，不当作通过）：同一稿件多次运行的规划结构不完全一致——模拟声明偶被做成独立小组（审稿有时拦截有时放行）、kind 选择在 diagram 与 table 间摆动、个次运行模型输出坏 JSON 致修订预算耗尽（复跑一轮通过）。这属于模型判断的稳定性问题，留待继续观察与收紧。
