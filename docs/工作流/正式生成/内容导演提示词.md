# 内容导演提示词

> 状态：当前正式生产契约。下一阶段的多表达运行时与有限代理方案尚未接入；在此之前不按目标架构改写本提示词。

本文是内容导演的稳定执行准则。正常生成时，内容导演一次读取完整原稿，一次输出整套逐页 Markdown 内容稿与轻量机器元数据；它不选择最终 Structure Group，不负责坐标、配色、组件实现或画面检查。

## 唯一内容源

`contentMarkdown` 是内容层级和正文的唯一事实源，不再平行维护“全文层级树”或另一份逐页正文 JSON：

- `#`：唯一页面边界；每个 H1 就是一页，其后首个引用块是本页叙事职责；
- `##`：页面最外层关系中的同级主节点；
- H2 下普通段落：该节点正文；
- H2 下列表：原稿明确提供的节点内支撑点；
- `###`：可选的节点内小标题，不产生新页面；
- 不使用 H4 及更深标题。

整套标题、核心结论和简短叙事弧保存于 `deckMetadata`，不再作为伪页面写进 `contentMarkdown`。

程序严格按这份 Markdown 编译现有 `DeckPlan / PageContent`。编译产物不能被结构提示、视觉导演或局部细化静默改写；需要修订时必须修改 Markdown 并重新编译。

## 判断优先级

1. 原稿证据真实性；
2. 原稿结构完整性；
3. 全稿叙事完整性；
4. 页面正式字号下的容量；
5. 当前核心结构能力的可承载性。

不得为了提高结构使用率改变关系、增加节点、补造分点或虚构数据。只有原稿确实没有可视化关系时才使用 `editorial`。

## 单次调用中的工作顺序

1. 通读完整原稿，在 `deckMetadata.narrativeArc` 中概括最大的叙事阶段；
2. 在各章节内识别可以独立承担一页职责的最小语义单元；
3. 用 H1 形成唯一页序和逐页职责；
4. 逐页判断最外层 Logic，用 H2 保留全部真实主节点；
5. 只把原稿明确提供的节点内下级内容写成列表；
6. 参考匿名 `structureCapabilities` 检查是否漏掉原稿已经存在、且后续结构需要的关系字段；
7. 输出完整 `contentMarkdown / deckMetadata / pageMetadata`，不在调用之间逐页往返。

普通原稿中的 Markdown 标题只表示来源组织，不决定 PPT 页数。只有原稿用完整行明确写出的“第 X 页”是硬页面边界，内容稿必须保持其页数与顺序。

## 机器元数据

`pageMetadata` 严格按 H1 顺序对齐，只保存 Markdown 不适合承载的机器字段：

- `logicIntent.logicId / reason / evidenceFragments / confidence`；
- 可选 `itemMetadata`，与本页 H2 同序等长，只保存 `emphasis / polarity`；
- 一至两个 `sourceBlockIds`；
- 复杂 Logic 必要时使用的 `relationBindings`。

元数据不得重复页面标题、叙事职责、H2 正文或列表。程序按 H1 顺序生成 `page-01 / page-02`，再生成稳定 item ID：`page-01-item-1`、`page-01-item-2`……

原稿进入模型前由程序按段落编号为 `source-001` 等稳定块。`sourceBlockIds` 必须从本次输入清单中选择，不允许模型抄写逐字锚点或自造 ID。程序根据 ID 生成 `sourceAnchors / sourceText`，因此 DOCX 换行、空段和标点不会再使语义正确的页面因字符串拼接失败。不同页面可以回看、重排或部分交叠原稿证据；完全相同的证据范围不能重复生成两页。`evidenceFragments` 若有轻微空白或标点偏差，由程序用已选来源块中的原文证据收口并写入修复日志。

普通 `editorial / parallel / sequence` 等关系直接由 Markdown 节点编译。复杂关系使用 `relationBindings`：

- `references` 只引用 `page.title`、`item:N.id/title/body` 或 `item:N.point:M`；
- `literals` 只填写 ID、枚举、布尔、数值或邻接矩阵；
- 人类可读标题、正文、标签、条件和结果必须引用 Markdown，不能在 JSON 再写一份。

编译后仍由现有 `PageContent` Schema 与结构引用验证收口；必要字段无法由原稿支持时保留真实 Logic 并失败关闭，不补写数据。

## 页面与容量

- 一页可以有多个 H2 主节点；开场、案例、论证和收束承担不同叙事职责时，应拆成不同 H1 页面。
- 不得把整章硬压成一个巨型并列、时序或卡片页，也不得为了增加页数重复内容。
- H2 标题不超过 10 个汉字，正文尽量 15–30 个汉字；正文与列表不重复。
- 页面总量或单项容量超限时，优先按不同叙事职责拆成两个 H1，并同步补齐两项元数据与各自可核对的来源证据；也可以压缩重复修饰，不能缩小字号硬塞。

## 调用与失败边界

内容导演正式调用关闭 thinking；真实运行已证明启用 thinking 容易长时间只返回推理、空 `message.content` 或截断 JSON，而关闭后能够更快形成完整结构化结果。

正常生产只调用内容导演一次。整次内容阶段共享唯一一次恢复预算，不再由模型 JSON 层和 Markdown 编译层分别重试。以下任一错误均最多让内容导演再调用一次：

- `MODEL_JSON_INVALID`；
- `MODEL_REQUEST_TIMEOUT`；
- `CONTENT_MARKDOWN_INVALID`；
- `CONTENT_METADATA_MISMATCH`；
- `CONTENT_CAPACITY_EXCEEDED`。

第一次编译先执行不增加 API 的确定性修复：按来源块生成原文证据，收口轻微证据偏差，并删除无法编译的可选关系元数据。仍失败时，程序才把完整 `contentMarkdown / deckMetadata / pageMetadata` 交回唯一修订轮。修订轮必须保留 H1 页序、H2/H3 页内内容、页面正文、Logic 和其他已合法元数据，只修改反馈明确指出的字段。

第二次仍不合法时，正式生产不再整条失败：程序按原稿连续片段生成 `editorial` 保底内容页，保留来源事实并在 `resilience-report.json` 标记降级。内容导演最多两次，视觉导演最多一次，因此正常整套是两次 API 连接，使用恢复后最多三次；确定性保底不增加 API。保底承诺的是“形成可审计、可渲染的忠实内容”，不是承诺与模型最佳编排同等质量。

内容导演不读取或选择资产 ID、Capability Key、Structure Group、容器、坐标、颜色、图标或组件槽位。语义明确但核心资产尚未覆盖时，保留真实 Logic 并报告 `asset-gap`。
