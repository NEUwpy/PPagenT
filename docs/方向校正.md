# 方向校正

本文用于防止长任务在实现过程中偏离 PPagenT 的主目标。它不重复[产品定义](产品定义.md)；产品边界以产品定义为准，当前优先级以[当前阶段](当前阶段.md)为准，本文负责说明近期取舍和停止条件。

开始长任务前，必须先读这三份文档。若任务要求与本文冲突，先停止并向用户确认，不得把一次技术实验自行升级为项目重构。

## 当前主目标

先在东北大学这一固定场景中证明：用户只提供原稿并选择主题，系统就能以较低运行成本，稳定生成结构清楚、视觉统一、原生可编辑的工作型 PPT。

PPagenT 服务的是数量最多的常规工作型演示，不追求覆盖所有开放场景，也不以每次创造全新视觉为目标。

## 本轮校正

1. **产品验证优先于继续设计架构。** 现有链路已经足以进入真实稿件压力测试。除非真实失败证明现有对象无法表达，否则不新增抽象层、Schema 或 Agent。
2. **建设期设计，运行时调用。** 昂贵的视觉探索、参数化和人工判断尽量在资产建设时完成；正式运行时，模型主要负责内容规划、语义判断、合法资产选择和参数填写。
3. **用能力覆盖率衡量资产库。** 不再把资产数量当进度。新资产应由真实稿件中的高频缺口驱动；Logic 按语义关系组织，一个 Logic 可以包含多个 Structure Group，每组适应已声明的数量和内容 State。
4. **主题与内容能力分层。** 当前已固定 `Shell + Content Frame` 几何：Shell 组织页面骨架，Skin 替换身份与主题值，Structure Group 只在 Content Frame 内表达。完整边界见[Shell 与 Logic 契约](Shell与Logic契约.md)。
5. **HTML/CSS 是 Structure Group 的内部构建表示，不是新产品格式。** 当前用它复现视觉语法并实现响应式数量扩散，再回编译为原生可编辑 PPTX；不因此建设面向任意 PPT 的通用转换器，也不改变 `.pptx` 交付目标。
6. **二层表达只增加槽位契约，不增加新 Agent。** 父 Structure Group 先按 State 求解真实 Content Slots，槽内再选择普通文字或已登记的一级子 Logic；子 Logic 不得改变父拓扑，当前最大深度固定为 1，没有合法子资产时回退为文字。
7. **检查保持必要且轻量。** 正式生成只保留确定性的字号、越界、重叠和容量门禁。建设期由维护者和用户看最终页面并纠偏；不为已确认结果重复制造哈希、全状态证据和多轮审查。
8. **产品优先，论文伴生。** 现在不为了论文扩建系统。只在产品运行中顺手保存成本、失败、覆盖率和用户修改等数据，等真实样本形成后再决定是否开展正式研究。

## 接下来按这个顺序做

### 1. 暂停既有稿件与压力测试

《让“六地”红》的继续校准、5–10 份真实稿件压力测试和学术实验系统全部暂停。已有真实稿件已经足以证明“AI 结构化 + 核心资产 + 确定性 PowerPoint”主路线可以运行；当前先验证新的内部表达架构。

### 2. 按四个检查点验证新链路

从已有案例 PPT 选择一个代表性来源页：

1. 先用 HTML/CSS 忠实表达来源页；
2. 再抽象成一个 Logic 下的 Structure Group，由同一组件生成不同数量状态并检查排版；
3. 把这些状态批量编译为原生可编辑 PPTX；
4. 打包成固定脚本，输入一段新文案并跑通完整链路。

四个检查点只比较：

- 最终画面；
- 原生可编辑性与转换损失；
- 版式扩散稳定性；
- 人工返工次数；
- 运行时间与 Token 消耗。

实验只回答这条链能否成立，不借机建设新的通用框架。

### 3. 固定 Shell 后继续验证组合

当前循环闭环 Structure Group 已闭合 HTML 单源到 Native 的最小链路，东北大学正文页的 Shell 几何与 Content Frame 已据来源模板固定。下一步先用它验证一个真实 Content Slot：父环形结构保持不变，槽内分别测试普通文字与一个已登记的小型子 Logic。正式组合目标是：

> Skin 填充身份 → Shell 提供页面骨架 → Content Frame 承载父 Structure Group → State 求解 Content Slots → 槽内放普通内容或一级子 Logic → 编译为 PPTX

只有组合验证通过，才决定是否据此重构现有主题和资产运行时。

### 4. 再恢复产品验证

新架构结论明确后，再恢复真实稿件压力测试、失败频率统计、实时 API 和最小用户端。产品优先、论文伴生的原则不变。


## 长任务开工卡

每个长任务开始前只需明确六件事：

- 本次要验证的一个问题；
- 输入稿件或来源页；
- 允许修改的系统部位；
- 可见产物；
- 完成标准；
- 何时停止并交给用户判断。

默认禁止：顺手重构邻近模块、批量扩资产、增加新的治理层、为低概率风险新增常驻流程、把候选技术写成既定架构。

## 决策状态

### 已确定

- 固定场景优先，东北大学为第一场景。
- 内容导演与视觉导演分工，运行时只调用已验证能力。
- 原生可编辑 PPTX 是交付物。
- 资产按语义关系家族组织，并声明版式扩散范围。
- 父 Structure Group 声明动态 Content Slots；二层结构只允许一级、只用核心资产，失败时退化为普通文字。
- 缺少合适结构 Structure Group 时退化为已登记的简单文字 Composition；简单排版仍不成立时再拆页或失败关闭，不现场自由绘图。

### 正在验证

- 更多来源页能否稳定形成忠实、可扩散的 Structure Group。
- 同一 Logic 下多个 Structure Group 是否足以支持视觉导演在整套尺度编排。
- HTML Structure Group 是否能稳定批量编译为原生可编辑 PPTX。
- `Shell + Content Frame + Logic / Structure Group` 是否值得迁移进正式运行时。
- Content Slot 是否能在不增加第二套坐标逻辑和新 Agent 的前提下承载一级子结构。
- 现有资产对真实工作型稿件的覆盖率。
- 低成本模型在双导演固定 Schema 下的稳定性。

### 暂不开展

- 全面重写渲染运行时。
- 面向所有场景的通用 PPT 生成。
- 大规模继续蒸馏但没有真实缺口依据的资产。
- 为论文提前建设完整 benchmark、训练模型、用户实验或复杂评审系统。
