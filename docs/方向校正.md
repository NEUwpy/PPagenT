# 方向校正：从固定填表转向 PPT 专用 Harness

> 更新日期：2026-09-04

本文只记录当前事实、已经确定的方向和下一步仍需验证的部分。产品最终形态见[产品定义](产品定义.md)，代码与资产现状见[更新日志](更新日志.md)。

## 当前状态

- `Shell + Content Frame`、35 个核心 Structure Group、HTML 资产审核、Native PPTX 编译、资产看板和当前双导演生产线均已形成基础。
- 第一轮结构资产集中建设已经结束。继续穷举完整结构图不能解决大多数真实稿件的适用性。
- 当前内容导演和视觉导演本质上仍是两次受 Schema 约束的模型调用：前者一次拆稿，后者从候选中填表；程序承担了过多页面决策。
- 当前正式视觉流程仍以“一页一个主 Logic／Structure Group／Composition”为主。它能交付，但对普通文字页、图片页和复合页面过于死板。
- Penguin Harness 试验只证明了一个窄循环可以运行，没有达到 Codex 式的稿件理解、工具使用和逐页编排质量；该试验不进入 `main`。

## 当前问题

已有资产并非没有价值，问题是调用方式过于刚性：

1. 一次性内容输出很难同时兼顾整稿叙事、分页、页面容量和后续视觉承载；
2. 一次性视觉选择只能“选候选、填字段”，不能先规划页面区域，再组合文字、图片和结构；
3. 程序把合法路径写得过死，轻微不匹配就会失败或退回单调正文；
4. 继续增加 Schema、分支、重试和兜底，会把系统变成补丁集合；
5. 把全部资产和源码一次性交给模型，又会造成 Token、延迟和选择噪声。

## 已经确定的方向

1. 下一阶段探索对象确定为 **可用于产品的 PPT 专用 Agent Harness**，放弃把一次或若干次孤立问答式 API 调用继续扩张成主架构。API 仍是 Harness 调用模型的底层接口；固定重答只保留为异常恢复，不再承担智能编排。
2. Harness 由总 Agent 调度内容导演和视觉导演。内容导演负责叙事与分页；视觉导演负责全稿节奏、页面版式、区域组合和 Skill 调用；总 Agent 负责状态、预算、局部反馈、QA 和交付。
3. 已有程序与资产不丢弃，而是封装或引用为 Skills。程序负责稳定执行，Agent 负责选择、组合和在允许范围内适配。
4. 视觉系统由并列的 `Skin` 与 `Layout` 组成；Layout 在 Skin 的 Content Frame 内组织 `Text / Media / Structure`，Structure 再按 `能力域 → Logic → 具体 Structure／Style Group` 渐进披露。Native QA 是公共执行层，不是另一类版式资产。
5. 正式目标链直接生成原生可编辑 PowerPoint。HTML 保留在资产入库、设计实验和审核看板，不再作为目标正式线每次运行的必经真源。
6. 核心 Skill 不在正式运行中被静默修改。运行时适配只属于本次稿件；晋升核心库仍需独立入库和用户确认。
7. 失败处理优先顺序为：精确调用 → 受限适配 → 多 Skill 组合 → 重组或拆页 → 成熟文字／图文兜底。不得用虚构内容或不可编辑图片兜底。

## 下一步只验证什么

先实现一个最小纵向切片，不全面重写：

- 选取一小段真实稿件，包含普通文字页、明确结构页和图文／复合页；
- 总 Agent 只调度内容导演和视觉导演两个子 Agent；
- 只封装少量代表性 Skills：一个整页 Composition、一个 Text、一个 Media、一个现有 Structure 和一个 Native QA；
- 视觉导演先给出页面区域与能力组合，再按需加载具体 Skill；
- 只允许一次页面级内容反馈和一次渲染后修正，记录调用、Token、耗时、fallback 和人工质量。

验证重点是：同一稿件是否比当前填表流程更完整、更自然、更稳定，以及提升是否值得额外调用成本。若最小切片不能明显改善结果，就先调整角色权责和 Skill 契约，不扩建完整 Harness。

## 尚未确定

- 采用哪一种 Harness／Agent SDK，或自行实现多薄的一层调度；
- 内容导演和视觉导演使用同一模型还是不同模型；
- 哪些页面需要渲染截图反馈，哪些只需确定性 QA；
- 运行时适配代码允许到什么粒度、怎样缓存和复用；
- `PageExpressionPlan` 是否继续使用，或被更轻的页面任务状态取代。

这些是实验要回答的问题，不先写成既定实现。当前生产线在新纵向切片通过前继续保留，不为“新架构”提前删除可交付能力。

架构与 Skill 契约先在 `main` 收束；文字／整页排版能力和图片区域能力随后分别在独立分支建设，验证后再按同一契约纳入，避免在基础对象未定时并行制造两套接口。
