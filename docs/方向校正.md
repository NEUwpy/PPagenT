# 方向校正

本文用于防止长任务在实现过程中偏离 PPagenT 的主目标。它不重复[产品定义](产品定义.md)；产品边界以产品定义为准，当前优先级以[当前阶段](当前阶段.md)为准，本文负责说明近期取舍和停止条件。

开始长任务前，必须先读这三份文档。若任务要求与本文冲突，先停止并向用户确认，不得把一次技术实验自行升级为项目重构。

## 当前主目标

先在东北大学这一固定场景中证明：用户只提供原稿并选择主题，系统就能以较低运行成本，稳定生成结构清楚、视觉统一、原生可编辑的工作型 PPT。

PPagenT 服务的是数量最多的常规工作型演示，不追求覆盖所有开放场景，也不以每次创造全新视觉为目标。

## 本轮校正

1. **产品验证优先于继续设计架构。** 现有链路已经足以进入真实稿件压力测试。除非真实失败证明现有对象无法表达，否则不新增抽象层、Schema 或 Agent。
2. **建设期设计，运行时调用。** 昂贵的视觉探索、参数化和人工判断尽量在资产建设时完成；正式运行时，模型主要负责内容规划、语义判断、合法资产选择和参数填写。
3. **用能力覆盖率衡量资产库。** 不再把资产数量当进度。新资产应由真实稿件中的高频缺口驱动，并按语义关系组织成可适应不同数量和内容状态的 Visual Skill 家族。
4. **主题与内容能力分层。** 当前把 `Shell + Content Frame` 作为候选边界：Shell 固定组织视觉语言和页面安全区，Visual Skill 只负责 Content Frame 内的表达。两者应能独立演进和组合。
5. **HTML/CSS 是候选内部技术，不是已决定的新产品路线。** 可以用一个最小实验判断它是否改善响应式布局、主题组织和版式扩散；在证明可编辑性、视觉质量和成本收益前，不整体改写现有 PowerPoint 运行时，也不改变原生 `.pptx` 交付目标。
6. **检查保持必要且轻量。** 正式生成只保留确定性的字号、越界、重叠和容量门禁。建设期由维护者和用户看最终页面并纠偏；不为已确认结果重复制造哈希、全状态证据和多轮审查。
7. **产品优先，论文伴生。** 现在不为了论文扩建系统。只在产品运行中顺手保存成本、失败、覆盖率和用户修改等数据，等真实样本形成后再决定是否开展正式研究。

## 接下来按这个顺序做

### 1. 收束当前真实稿件

完成《让“六地”红》当前版本的用户校准。发现问题时只修通用提示词、Schema、Skin、整页骨架或核心资产，不制作稿件专属旁路。

### 2. 做一个最小技术对照

只选东北大学 Shell 和一个常见的并列关系 Visual Skill，覆盖 3、4、5、6 项。比较现有直接 PowerPoint 方案与前端式布局方案；如果确有必要，再加入 HTML/CSS → PPTX 路线。只比较：

- 最终画面；
- 原生可编辑性与转换损失；
- 版式扩散稳定性；
- 人工返工次数；
- 运行时间与 Token 消耗。

实验只回答“哪种内部实现更合适”，不借机建设新的通用框架。

### 3. 进入真实稿件压力测试

选择 5–10 份类型明显不同的真实稿件，连续使用同一正式入口。先观察系统在哪里失败，不预先大批扩充资产。

每次只记录最少但有用的数据：稿件类型、页数、导演调用成本、每页关系与最终资产、无候选页面、渲染失败、人工修改和最终是否接受。

### 4. 用失败频率安排开发

把问题归入内容规划、关系判断、整页编排、资产覆盖、Skin/排版或渲染。优先修复反复出现的问题；只有高频资产缺口才进入入库队列。覆盖率采用“多少页面无需新增资产即可完成”，不采用“已有多少个资产”。

### 5. 再接实时 API 和产品入口

在最小技术路线和当前 Skin 稳定后，接入真实 DirectorProvider。产品验证阶段先做少量重复运行检查模型抖动；同稿件 10 次、完整基线和用户研究属于后续论文实验，不先变成日常门禁。

当 10–20 份真实稿件能够稳定运行后，再考虑最小用户端：上传 Markdown/Word、选择 Skin、下载 PPTX。

## 长任务开工卡

每个长任务开始前只需明确六件事：

- 本次要验证的一个问题；
- 输入稿件或来源页；
- 允许修改的系统部位；
- 可见产物；
- 完成标准；
- 何时停止并交给用户判断。

默认禁止：顺手重构邻近模块、批量扩资产、增加新的治理层、为低概率风险新增常驻流程、把候选技术写成既定架构。

## 决策状态

### 已确定

- 固定场景优先，东北大学为第一场景。
- 内容导演与视觉导演分工，运行时只调用已验证能力。
- 原生可编辑 PPTX 是交付物。
- 资产按语义关系家族组织，并声明版式扩散范围。
- 缺少合适资产时失败关闭，不现场自由绘图。

### 正在验证

- `Shell + Content Frame + Visual Skill` 是否应成为正式内部边界。
- 前端式布局或 HTML/CSS 是否比当前直接 PowerPoint 方案更适合版式扩散。
- 现有资产对真实工作型稿件的覆盖率。
- 低成本模型在双导演固定 Schema 下的稳定性。

### 暂不开展

- 全面重写渲染运行时。
- 面向所有场景的通用 PPT 生成。
- 大规模继续蒸馏但没有真实缺口依据的资产。
- 为论文提前建设完整 benchmark、训练模型、用户实验或复杂评审系统。
