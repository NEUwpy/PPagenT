# 当前阶段

本文只记录 PPagenT **现在**在做什么。历史变化统一见[更新日志](更新日志.md)，产品定位与长期边界见[产品定义](产品定义.md)，Shell 和组件颗粒度见[Shell 与 Visual Skill 契约](Shell与Visual Skill契约.md)。

## 一句话状态

PPagenT 当前处于 `0.8.x` 的生成架构收口期：固定场景下的双导演与核心资产调用已经跑通。循环闭环正在验证新的单源链路——HTML 同时承担设计与最终布局，通用编译器把浏览器求解结果转换为 Native PPT；其余正式结构暂保留旧 Native Builder。过去由共享通用组件提供的预览不计为迁移完成。

## 现在正在做

1. **固定 Shell。** 东北大学正文 Shell 使用 `1280×720` 画布，Content Frame 为 `1170×492 @ (55,166)`；标题、Logo、页码和页脚属于 Shell，Style Group 只在 Content Frame 内工作。
2. **先验证统一编译，再继续扩库。** 新 Style Group 用 HTML 完成审美与 State 扩散，并由通用 HTML → Native 编译器生成 PPT；正式包用 `asset.json + review.mjs + component.css + 共享预览参数 + example.pptx` 表达，不再复制一份资产专属布局代码。
3. **建立页面角色 Skill。** `备选资产/目录/目录卡片组-001` 已形成 3–7 项响应式候选和审核稿，仍在备选库等待用户确认；它不会在确认前进入正式生成线。
4. **校准低成本导演调用。** `deepseek-v4-flash` 已跑通真实 API。内容导演负责叙事与来源语义结构，视觉导演负责合法 Style Group、组件绑定和整套节奏；程序负责候选过滤、参数映射和质量门禁。

## 已经成立的底座

- 正式输入是 `稿件/<文件名>` 与 Skin；原始 PPT 来源唯一从 `PPT源/<文件名>` 读取。
- 正式生成只发现 `status=core` 的自描述资产包；候选资产必须经用户明确确认才能晋升。
- HTML Component 是布局唯一真源；通用编译器是把最终 DOM/CSS/SVG 转成原生 PPT 对象的正式出口。
- 无合法结构 Style Group 时，程序仍提供已登记的简单文字 Composition：列表、主次聚焦、反向聚焦、单观点和双观点。简单排版也无法满足容量与字号时，才压缩、拆页或失败关闭。
- `items[]` 表示主关系节点，来源本来存在的节点内分点进入 `items[].points[]`；组件需要把长内容整理成重复短条目时，由 Style Group 声明 `contentContract.bindings`，视觉导演填写 `CompositionPlan.componentBindings`，程序确定性校验数量、字数、来源与内容覆盖。
- PPA 看板只把明确声明为 `asset-specific-html` 的组件计入 HTML 审美工作台覆盖；当前并列能力卡片和循环闭环可实时切换 State，其余资产在专属 HTML 迁移完成前明确显示“尚未迁移”，不再展示通用假复现。
- 正式命令默认使用 production 模式，不调用内容/视觉审查 Agent；独立审查只属于可选研发模式。DeepSeek Provider 当前还会对程序命中的高置信结构片段发起至多 8 个并行小型解析请求，这是为解决长上下文漏分点而保留的补偿机制，不应被误记为第三个导演。2026-08-14 的两页最小 A/B/C 证明不能直接删除结构提示，但把逐 cue 请求合并为一次批量预读，可在本样本保持结构正确的同时把请求数从 4 降到 2、时间从 14.6 秒降到 9.4 秒；生产实现尚未迁移。

## 当前完成标准

- 每个新 Style Group 有明确来源、页码、HTML 审美确认状态、适用关系、数量/容量范围、媒体约束和 Content Frame 边界。
- 用户审核的 HTML State 必须由同一个通用编译器直接生成 Native 结果；不得再为同一 Style Group 手写一份语义布局。
- 只制作会改变真实布局的主要 State，不要求所有 Style Group 统一支持 3–8 项，也不做“数量 × 三档字数”的全状态穷举。
- 来源页用于理解关系、拓扑和审美起点；HTML 是实际设计与优化工作台。用户先确认 HTML 的美观与响应状态，再编译 PPTX 检查转换损失和 Skin 效果。
- 用户看过代表性状态并明确确认后，候选才可进入核心库和正式候选发现。
- 基础能力覆盖形成后，再用真实稿件检查 Visual Skill 调用率、正文兜底率和需要人工修改的页面；现阶段不启动大规模 5–10 稿压力测试。

## 本阶段不做

- 不让 AI 自由绘制整份 PPT，也不在正式运行时临时创造结构图。
- 不建设面向任意网页的通用转换器；来源 HTML 必须先蒸馏为 PPagenT 可编译组件，也不把截图或整页图片当作最终 PPT。
- 不新增 Agent、Schema 层级或治理流程，除非真实失败证明现有对象无法表达。
- 不恢复默认全状态穷举、反复哈希和重型证据闭包；这些只保留为按风险启用的诊断工具。
- 不自行晋升候选资产，不擅自继续《让“六地”红》稿件。
- Luna 只负责来源 PPT 的蒸馏与入库，不参与正式生成线。

## 正式主线

> 原始稿件 + Skin → 内容导演 → `DeckPlan` / `PageContent` → 视觉导演意图 → 程序生成合法候选 → 视觉导演编排 → `LayoutDecision` / `RenderPayload` → 已登记 HTML Component → 通用 Native 编译器 → 原生可编辑 PPTX

这些名称是可审计的数据对象，不是同等数量的 Agent。生产模式的导演基线是一次内容导演调用和两阶段视觉导演调用；启用结构线索解析器时会另有局部并行小请求。只有来源、Schema、容量或合法性检查失败时，才在受控次数内重答。

## 下一检查点

下一步是在 PPA 看板同时审核循环闭环的 HTML 与统一编译 Native 结果，并检查 3–6 步 State。该闭环通过后，再逐项迁移其余正式 Style Group；迁移的是 HTML 标注与通用编译兼容性，不再新增资产专属 Builder。
