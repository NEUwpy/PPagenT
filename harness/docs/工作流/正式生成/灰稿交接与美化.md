# 灰稿交接与美化

## 前后两段的边界

2026-09-28 分支汇聚后，“文稿→分页稿→灰稿”和“灰稿→美化→成稿”作为同一系统的前后两段保留。灰稿是内容与空间计划的可审阅中间产物，便于分别固定输入和验证；分支名不再决定执行边界。

前半段形成页面任务、实文、来源、归属、关系、布局选择与区域映射。后半段消费同一计划版本，根据关系和承载条件选择已接入结构、图表、流程等能力，绑定内容并应用风格规则与参数。程序负责已选能力的几何、样式和原生构建。内容、关系或分页改变时返回规划，重新生成受影响预览。

灰稿人工验收与程序校验分别保留状态；不能把待审灰稿自动记成已认可。固定灰稿验证美化只证明后半段，手工编写的灰稿不证明自动分页能力。下文保留已有登记机制与历史证据，目标契约不要求立即另建 GreyPagePlan 文件。

## 2026-09-29 实际接口与迁移边界

正式灰稿入口已接受同组文字视觉块映射，原始组、来源、label/body/note 与映射进入交接目录。灰稿候选发布同时保存 deckBrief；旧状态可从已交付计划恢复，缺失则拒绝构建。`component-gray-regions` 允许纯文字不绑定 structure，一个图示精确绑定 sourceLocation，多图示仍返回能力缺口。

本轮固定计划与固定视觉方案经实际工具和中性 Skin 编译、原生文字及全页预览验证，见[实施记录](../../../experiments/visual-block-mapping-20260929/README.md)。该样本的选择/审稿由脚本提供，不是自主工作流通过。纯文字可逐组选择 `program:"source-text-v1"`，程序负责原区排字和映射保持，不接受坐标或正文。非文字保留 `regionVisuals.layout` 兼容路径，两种模式不混用。新程序处于建设候选，当前 v5 引擎缺少实际字号/行盒证据，正式 check_pages 仍失败；已保存原生产物和重导入预览供审阅。用户待审状态不得自动改为验收通过。

## PPA 看板入口

顶部“灰稿版式”，或实时看板 `/#gray-drafts`。当前只登记一个模拟灰稿中间产物入口，内部使用 24 页覆盖版来实验不同版式；10 页初版保留在实验目录中作历史材料，不再作为看板入口。该段描述 2026-09-26 的登记起点，后续美化已开展实验，人工质量验收仍须逐项核对；不能把模拟样例标成 main 线已生成或已验收的真实稿件。

看板支持切换批次、逐页快照、点击放大、按布局和结构参考尺度筛选，以及下载可编辑 PPT、交接数据和内容提纲。快照直接读取现存文件，浏览和刷新不会调用规划、渲染或结构生成程序。中间产物不计入四个能力域的资产数量或审批完成度。

2026-09-27 历史核查：此前第 01 页及后续 24 页双 Skin 产物均由实验脚本手工构建，没有经过正式 Harness 制作流程。它们不作为工作流测试证据，已撤下看板美化登记，文件保留追溯。当时正式灰稿到美化的交接尚未打通；不得按测试页码、标题或测试内容添加特化分支来代替通用能力。

当前已合入 --gray-state 交接与 regionVisuals 局部方案实现，见[灰稿视觉编排](灰稿视觉编排.md)。这证明接口和实验存在，不证明资产化生产或跨稿美化质量通过；旧手工样例仍不改记为正式运行。

## 登记下一份灰稿

轻量目录为 `catalog/gray-drafts.json`。当前只登记一个灰稿版式入口；该入口指向一个灰稿状态和其当前产物目录。未来要更换模拟内容，更新同一入口指针并保留旧实验目录，不要把每一次版式尝试扩成新的看板入口。前后两段引用同一内容真源与能力库，不复制原稿生成程序，不自动扫描或改写历史运行结果。

读取 `state.json` 中的页面与 `grayDraft.humanReview`。当前 revision 的产物目录以 `grayDraft.artifactDirectory` 为准；没有该字段才采用状态文件所在目录。推荐登记项目相对路径；旧状态中的绝对路径仅在仍指向当前项目时可用，迁移项目后需修正指针，不能静默回退到旧文件。

交接产物包含：

- `state.json`：页面实文、信息归属、关系说明、区域与人工审阅状态。
- `gray-draft.pptx`：与该状态对应的可编辑灰稿。
- `preview-index.json`：每个 `pageId` 对应当前快照文件；对应 PNG 一同保留。
- `content.md`：供人工阅读的内容提纲，可选。

交接数据下载目前是原始状态 JSON，引用路径仍以项目为基准，不是已打包的跨机器移交压缩包。未来美化稿应另存并关联输入灰稿版本，不能覆盖灰稿原件或根据程序检查自动修改人工验收状态。正式验证应记录真实入口、输入灰稿版本、模型与规则版本、结构调用和渲染证据；看板只展示对应运行产物。用户已要求覆盖 24 页，但手工样例不计入完成数量。

## 实现与验证

`src/tools/gray-draft-catalog.mjs` 读取登记和状态；`serve-logic-dashboard.mjs` 提供注册 ID、文件类型与页码限定的只读文件路由。图片、PPT 和 JSON 支持 ETag 校验，未变化返回 304；没有静态文件生成兜底。缺失产物明确显示不可用，避免加载旧 revision。

对应测试覆盖当前 revision 指针、待验收状态、缺失文件、非法 ID／页码／文件类型与项目边界。看板通过数据接口读取，不需要另建实验 HTML 服务。`PPA看板.exe` 启动器加载仓库代码，重启看板服务即可使用新增入口。
