# 生成线架构决策

2026-09-30 现行决策：建设和投入使用都采用一条两段式生成线，只有两个大里程碑：**稿件到灰稿、灰稿到成品**。页面表达契约是两段之间唯一的共同契约，灰稿是契约的编译视图。

## 规范生成线

```text
main：原稿
  → 语义理解、分页和逐页内容
  → 页面表达契约
  → 一级版式/二级结构候选
  → JEV 选择合法候选
  → 程序做区域/槽位绑定与容量求解
  → 灰稿

home：冻结灰稿契约
  → Skin 与风格规则
  → 参数化布局/结构资产
  → 程序测量与原生构建
  → 成品 PPTX + 完整预览 + 检查证据
```

### main 的职责

- 负责稿件理解、分页、页面目的、主题句、来源、主次和必要关系。
- 负责提出页面表达需求；只从建设阶段已登记的版式/结构候选中选择。
- JEV 只返回命名候选（如 `layoutId`、`variantId`、`structureGroupId`）；程序验证候选合法性、容量和内容绑定。
- 灰稿编译后冻结页序、内容、关系、表达、区域和槽位，供用户与 Codex 建设检查。

### home 的职责

- 接收冻结契约，不重做分页和语义解释。
- 选择 Skin、风格和已实现的参数化资产，在槽位和容量边界内填充同一内容 ID。
- 负责测量、几何、原生可编辑对象、导出、预览和证据；缺能力就返回缺口。
- 以模拟灰稿建设美化原则是建设行为，不等于投入使用时增加视觉模型。

## 关键取舍

- 不把表单做成第二个正文源：表单只是契约的编辑/检查投影。
- 不让 JEV 编坐标、写制作代码或自由绘图；确定性程序掌握绑定、测量和渲染。
- 一级页面版式负责整页分区；二级结构负责区域内部表达，二级可省略。
- “内容不多不少”由页面目的、语义完整性和能力容量共同判断，不用统一字数阈值。
- 灰稿冻结语义和布局语义，Skin/风格只在声明的样式边界内变化；不能因美化重新规划页面。
- 稳定性按模型重理解、固定契约回放、跨稿闭环分别验收；“十次有九次相近”暂是工程目标。

## 产品与建设边界

建设阶段由用户与 Codex coworker 完成资产、规则、程序、视觉检查和阶段性合并；Codex 的视觉能力不进入产品。投入使用只有 DeepSeek v4.1 Flash、JEV 和确定性程序。生产工作台是日志编译的调试工具，不是产品功能。

当前实现优先复用 `gray-plan-3`、plan/state、来源绑定、测量和现有原生构建；JEV 已接入灰稿布局选择。完整语义编译、跨关系候选、参数化结构覆盖和完整灰稿到成品仍未完成。旧接口、旧 stage runner 和历史实验只作兼容/证据，不得作为新流程调度依据。

本页不重复维护里程碑状态；小交付和验收证据见[项目进度](../../方向讨论/页面编排能力计划.md)。
