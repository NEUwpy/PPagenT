# E 审查方法审计

## 审计结论

`review-03.md` / `findings-03.json` 应保持原样。本文件只诊断当时的审查机制，不改 PPT，不改既有结论文件，也不判断内部产品实现是否真实存在。

审计确认了两类漏检：

1. **字号门禁漏检是确定的程序与判读错误。** `E2-font-gate.json` 对 SHA-256 与 revision-02 候选一致的 PPTX 返回 `fail`，指出 3 个 31.0 设计像素对象；我当时虽抽取到了对应的 23.25 pt，但把它错误解释为允许的符号/关系字号，并漏掉了其中一个正文句。
2. **来源忠实漏检是确定的方法覆盖不足。** revision-02 的第 7、12 页仍然包含 F-source-audit 识别的无直接依据机制。我当时只按页面主题和原稿段落做高层归纳，没有建立逐条页面主张的“直接依据／可标注归纳／无直接依据”台账，因此把规则或内部流程式语言误当成原稿支持的提炼。

## 一、字号门禁为什么漏检

### 门禁实际报告了什么

`E2-font-gate.json` 的 `status` 为 `fail`，冻结设计字号只有 `[13, 15, 17, 21, 25, 48, 58]`。它列出：

- `ppt/slides/slide2.xml`，对象 `id=5`，正文句“做 PPT 真正贵的，不是把文本框拖到左边还是右边。”，`actualDesignSize=31.0`；
- `ppt/slides/slide5.xml`，对象 `id=12`，符号 `≈`，`actualDesignSize=31.0`；
- `ppt/slides/slide10.xml`，对象 `id=19`，符号 `≠`，`actualDesignSize=31.0`。

我对同一 revision-02 候选重新读取 XML，得到同样的 23.25 pt，即 `23.25 / 0.75 = 31.0` 设计像素：

```text
slide=2 objectId=5  text=做 PPT 真正贵的，不是把文本框拖到左边还是右边。  xmlSz=2325 pt=23.25 designPx=31
slide=5 objectId=12 text=≈                                             xmlSz=2325 pt=23.25 designPx=31
slide=10 objectId=19 text=≠                                            xmlSz=2325 pt=23.25 designPx=31
```

这三项都真实存在于当前候选；不是渲染误差，也不是继承字体未解析导致的猜测。

### 我当时的错误机制

当时的检查过程先从 XML 汇总字号，再把 11.25、12.75、15.75、18.75、36、43.5 pt 映射到规则角色；看到 23.25 pt 时，我把它写成“只用于规则允许的符号 `≈`、`≠`”，并在 `findings-03.json` 中增加了没有来自冻结门禁的 `allowedSymbolSizePt: 23.25`。这一步有两个可证实的错误：

1. 冻结规则列出“符号可略大于一行字”的视觉描述，但没有授予 31 设计像素的数值例外；E2 门禁明确把 31 判为 `Outside frozen v3 size palette`。我把视觉偏好擅自升级成了数值白名单。
2. 23.25 pt 同时用于第 2 页的长正文句，它不是符号。我在以字号值聚合时没有保留“字号 × 对象角色”的逐对象强制检查，因而把正文漏在符号解释之后。

因此，`review-03.md` 中“23.25 pt 只用于规则允许的符号”和“未发现未登记文字字号”的说法均不成立。这里不确定的部分只有规则是否还存在另一个未提供的符号例外；在当前冻结规则和 E2 回执范围内，没有证据支持该例外，所以应按门禁失败处理。

### 应如何防止同类漏检

字号检查必须先执行实际 XML 门禁，再做视觉角色判断：对每个有文字的文本运行保留页面、对象 ID、文字、字体、字号和设计像素，不允许先按字号聚合后再凭语义放宽。任何对象超出冻结白名单都应阻止 `APPROVE`；符号如需例外，必须出现在冻结规则和门禁白名单中，而不能由审查者现场添加。

## 二、来源忠实为什么漏检

### 第 7 页：当前 revision-02 仍有同样的具体机制

我直接从 revision-02 PPTX 的 `ppt/slides/slide7.xml` 读取到：

```text
负责论证、页面职责、提炼、来源与语义约束。
负责区域、媒介、阅读关系与容量反馈。
共同形成初模。
页面职责＋提炼后的实文＋宏观区域和阅读关系。
内容与空间在同一轮策划中共同调整。
```

`revision-02/rendered-final-v2/slide-7.png` 也实际呈现了这些句子。F-source-audit 对 revision-01 已逐条指出“来源与语义约束”“容量反馈”“共同形成初模”以及“内容与空间在同一轮策划中共同调整”没有原稿直接依据；revision-02 没有改变这些文字，因此该来源问题仍然相关，不能因候选版本不同而视为自动关闭。

直接回查唯一原稿 `input/manuscript.md`：`来源与语义约束`、`容量反馈`、`共同形成初模`、`同一轮策划` 均无匹配。原稿第 73 行支持内容导演和视觉导演的基本职责，但不支持这套被写成确定产品流程的协同机制。

### 第 12 页：当前 revision-02 仍有闭环产品机制

我直接从 revision-02 PPTX 的 `ppt/slides/slide12.xml` 读取到：

```text
理解 / 编排 / 构建 / 审查 / 修正
回到上游

方向：理解 → 编排 → 构建 → 审查 → 修正

```

`revision-02/rendered-final-v2/slide-12.png` 实际呈现了水平箭头、回流提示和右侧四项清单。直接回查原稿：`Skin`、`实际渲染`、`回到上游`、`修正`、`同一轮策划`、`容量反馈`、`来源与语义约束`均无匹配；“审查”只在第 120 行以建设期视觉模型的资产理解与审查出现，并不能支持交付环节的“实际审查”节点。原稿第 120 行支持“真实任务中持续校准”，但不能单独推出一个正式五步闭环、具体回流点或四项校准输入清单。

因此，第 12 页的标题“持续校准的生产过程”可以视为对原稿第 120、122 行的归纳；具体的五步流程、回到上游、Skin 清单和实际审查机制则属于更具体的产品事实，仍缺少唯一事实来源的支持。

### 我当时的错误机制

我在 revision-02 复核时做了视觉和结构核对：看到第 7 页的两栏职责、第 12 页的箭头闭环变得清楚，就把“关系表达已可读”误当成“关系事实有来源”。同时，我将“内容导演/视觉导演”“代码检查”“持续校准”等原稿中的宽泛词语作为证据，直接覆盖了页面新增的具体动作和状态，没有逐句检查新增名词、动作、回流点和流程清单。

这不是“没有看到文字”的漏检，而是证据粒度错误：

- **页面级判断**：主题与原稿大致一致；
- **实际应做的主张级判断**：每个具体职责、流程节点、回流关系、机制清单都要标为直接支持、跨段归纳或无直接依据。

我当时使用了前一种粒度，却在报告中写成了后一种强结论“原稿关键事实、节点、限定和关系无阻塞缺失”。该强结论没有相称的逐条证据。

### 应如何防止同类漏检

来源审查应先从 PPTX 全部文本和可见关系建立页面主张台账，再回到原稿逐条标注：

1. 直接逐字依据；
2. 可由多处原稿合并得到且需标作“归纳”的表达；
3. 原稿没有、但规则或内部流程可能提供的表达；
4. 原稿和规则都无法支持的表达。

第 3、4 类不能在原稿唯一事实来源的审查中当作通过。视觉关系修复只关闭“图上是否看得懂”，不能关闭“关系是否由原稿支持”。

## 三、为什么当时会整体判定 APPROVE

当时的审查覆盖了 13 张 PNG、候选 XML 的对象类型、颜色、字体、字号汇总和主要页面关系，但覆盖方式存在两个断点：

- **门禁断点**：没有读取或执行 E2 的实际失败回执；手工汇总后擅自创造了符号字号例外，也没有逐对象保留正文角色。
- **来源断点**：没有建立 claim-level 来源台账；把规则语言、设计语言和从多段原稿得到的产品方向混在同一个“faithful compression”桶中。

所以，“看过所有页面”“对象是原生的”“关系图已经可读”都不能推出“字号全部合规、没有来源缺失”。`findings-03.json` 的 `findings: []` 是审查覆盖不足后的错误空集，不是这些问题不存在的证据。

## 四、可确定与不可确定的边界

**可以确定：**

- E2 回执的候选 SHA 与 revision-02 PPTX 相同；3 个 31 设计像素问题真实存在。
- revision-02 第 7、12 页仍包含上述文本；原稿对多个具体词语无匹配。
- 我当时的检查记录没有执行逐对象冻结字号门禁，也没有完成逐条主张来源台账。

**不能由本次审计确定：**

- 内部产品是否实际上已经实现第 7、12 页描述的协同与闭环流程；这需要另一个被授权的产品事实来源。
- 31 设计像素符号是否有未纳入当前冻结规则的正式例外；现有 E2 回执和冻结字号数组不支持该例外。
- F-source-audit 对 revision-01 的结论是否代表制作端曾经阅读它；本审计只直接比较其记录、原稿和 revision-02 当前产物，不对制作行为作因果推断。

## 审计后的最低检查协议

后续 E 审查若要给出 `APPROVE`，至少要同时有：

- 实际 XML 字号门禁为 pass，且候选 SHA 与被审文件一致；
- 每个有文字对象都能回指一个冻结角色和允许字号，符号不另行现场豁免；
- 每页所有新增主张、动作、关系、条件、回流点和机制清单均有原稿证据或明确标注为概念性归纳；
- 视觉检查、对象/几何检查、文字角色检查和来源主张检查分开记录；任何一个检查未执行或失败，都不能合并成总体 APPROVE。
